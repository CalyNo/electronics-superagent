# 08 AI 密钥与模型分配

> 本文解决三个问题：**要几把 key**、**每把 key 归谁用**、**怎么保证 key 不被滥用也不会成为单点**。

## 1. 先立三条原则

| 原则 | 含义 | 反面做法 |
| --- | --- | --- |
| key 是**容量单位**，不是权限单位 | 一把 key 只代表"一份配额 + 一个可独立吊销的凭据"。谁能让系统干活，由 Policy 决定，与 key 无关 | 用 key 区分"能干什么"（如给质量部单独一把 key 表示他们只能提质量问题） |
| 按**角色**分池，不按人/任务分 key | 系统里只有 4–5 种调用形态，池子数量就等于形态数量 | 每个工程师、每个项目、每张工单各配一把 key |
| key **永不进入执行器环境** | 执行器只会拿到一个指向本地网关的地址和短期票据；真实密钥只在网关进程内存里 | 把 `API_KEY` 写进 worker 的 env、`.env`、仓库配置、工单目录 |

第二条原则是本方案与"随便发几把 key"的分水岭。原项目 `setup` 阶段会剔除名字含 `KEY/PASSWORD/SECRET/TOKEN` 的环境变量，并把 `gh`、`lark-cli` 换成 `<stateDir>/worker-bin` 里的垫片——**同样的手法用在模型密钥上**：执行器看不到密钥，只看到一个本地端点。

## 2. 成本结构决定了分配比例

分配比例不该凭感觉，应看 token 花在哪。以一张典型的 S3 工单（生成过程流程图 + PFMEA + 控制计划）为例：

| 环节 | 单次调用 token | 每工单次数 | 占比 | 特征 |
| --- | --- | --- | --- | --- |
| 准入 Gate | 0（纯规则） | — | 0% | 不调模型 |
| Assessment 研判 | 3k–8k | 2–5 | ≈2% | 高频、短、要快、要稳 |
| 执行器主循环 | 20k–60k | 20–60 | ≈85% | 长上下文、多轮工具调用、要强推理 |
| 结果汇总与回写 | 2k–5k | 1–2 | ≈5% | 短、格式化输出 |
| 图纸/扫描件识别（S2、S4 才有） | 2k–10k | 0–10 | ≈8% | 突发、单价高、多数工单为 0 |

结论：

1. **执行器池必须占绝大多数配额**，它是唯一会把日预算烧穿的角色；
2. **研判池要独立**，因为它高频且延迟敏感——一旦和长任务共用一把 key，一张大工单就能把研判卡住，整条链路停止接单；
3. **识别池要单独封顶**，它单价高且用量不可预测，必须能被硬截断而不影响主流程。

## 3. 五类角色池

| 池 | 谁在用 | 能力档位 | 关键约束 | 单实例 key 数 |
| --- | --- | --- | --- | --- |
| `router` | Assessment 研判、任务分类、阶段判定 | 中档 + 低延迟 | p95 ≤ 5s；失败不得阻塞接单（降级为 `unavailable`） | 2（主 + 备） |
| `worker` | 五类阶段执行器 | 强推理 / 强编码 | 单工单 token 硬上限；并发 = `maxWorkers` | 3（2 主 + 1 热备） |
| `doc` | 长文档生成（DFMEA、PPAP 包、8D 报告） | 长上下文 + 中高档 | 可异步、可排队、可用更便宜档位 | 1–2 |
| `vision` | 原理图、PCB 截图、扫描件、客户图纸 | 多模态 | 独立日预算；禁止外部出境时必须走私有化端点 | 1–2 |
| `embed` | 模板检索、历史工单相似度（可选） | 嵌入模型 | 可复用 `router` 的账号 | 0–1 |

### 3.1 按阶段选模型（能力匹配，不只是省钱）

| 阶段 | 预设 | 建议档位 | 理由 |
| --- | --- | --- | --- |
| S1 策划 | `planner` | 中档 | 结构化文本 + 计划排布，规则性强 |
| S2 产品设计 | `designer` | 强推理 + 多模态 | DFMEA 需要因果推理；要读原理图 |
| S3 过程设计 | `process` | 强推理 | 过程流程图 / PFMEA / 控制计划三者必须一一对应，一致性要求高 |
| S4 验证 | `verifier` | 中档 + 工具执行 | 主要是跑测试、算 Cpk、填表，靠脚本而非模型 |
| S5 量产准备 | `releaser` | 中档 + 严格校验 | 清单核对与打包，宁可慢不可错 |

**不允许的降级**：主模型不可用时，不能悄悄换成弱模型继续生成 DFMEA / 控制计划 / PPAP。质量文档的"看似齐全、实则空洞"比直接失败危害大得多。此时应 `report(blocked)`，把"模型不可用"作为一条待人工决策抛回飞书。

## 4. 推荐配比（可直接抄）

以单实例、`maxWorkers: 4`、日 30–80 张工单为基准：

| 方案 | router | worker | doc | vision | 合计 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| 最小可用（MVP） | 1 | 2 | 0（并入 worker） | 1 | **4** | 单项目试跑、`observe` 模式 |
| 推荐（小规模生产） | 2 | 3 | 1 | 1 | **7** | 单产品线、日 ≤ 80 单 |
| 稳健（多产品线） | 2 | 4–6 | 2 | 2 | **10–12** | 2–3 条产品线、跨厂区 |

扩容规则（按顺序判断，不必同时满足）：

1. **配额不够** → 加 `worker` key。判据：任一 key 的 TPM 水位连续 15 分钟 > 70%，或 429 率 > 1%。
2. **并发不够** → 先加 key，再加 `maxWorkers`。每把 key 承载 2 个并发执行器较稳；`maxWorkers` 不要超过 key 数 × 2，否则限流会把重试风暴放大。
3. **故障不够隔离** → 加异构厂商的备 key（不同 provider，同一档位）。同厂多 key 只能解决配额，解决不了厂商级故障。

> 一把 key 打天下为什么不行：研判的短请求与执行器的长请求抢同一份配额；一次 429 风暴会让整条链路停摆；成本无法归因到角色；泄露时影响面最大，且轮换必然中断服务。

## 5. 并发与限额算式

```
峰值 TPM  ≈ maxWorkers × 单工单平均 TPM
          = 4 × 50k ≈ 200k TPM
所需 key 数 ≈ max( 2 , ceil(峰值 TPM / 单 key TPM 限额) )
并发上限   = key 数 × 单 key 安全并发（默认 2）
```

三条实用规则：

- **按 TPM 而不是 RPM 估**。Agent 的调用次数不多（20–60 次），但每次上下文很大，瓶颈几乎总在 token 侧。
- **每 key 留 30% 余量**给重试与突发，不要按 100% 水位配 key。
- **重试不得打回同一把 key**。网关用"最久未失败"策略选 key，配合指数退避 + jitter，避免自我 DDoS。

## 6. 关键机制：本地模型网关

```
执行器 ──(LLM_BASE_URL + 短期票据)──▶ 本地网关 :8787 ──(真实 key)──▶ 模型厂商
                                        │
                                        ├─ 按 X-Ticket-Id 选池
                                        ├─ 限流 / 排队 / 重试 / 换 key
                                        ├─ 按工单记账与预算硬截断
                                        └─ 审计日志（只记 token 与工单号）
```

网关要做四件事，缺一件这个设计就不成立：

| 能力 | 做法 | 不做的后果 |
| --- | --- | --- |
| **凭据隔离** | 网关持有 key；执行器只拿到 `http://127.0.0.1:8787/v1` 和随工单生成、随工单销毁的票据 | 任一执行器被提示注入或误操作即可泄露全部 key |
| **按工单预算** | 累计 token 达 80% 告警、100% 挂起并 `report(blocked)` | 一张跑飞的工单烧掉整月预算 |
| **选池与换池** | 依据请求头 `X-Role`（router/worker/doc/vision）+ `X-Ticket-Id` 路由；失败自动换池内下一把 key | 客户端各自重试，风暴不可控 |
| **记账与审计** | 每请求记 `{ticketId, stage, role, keyId, tokensIn/Out, cost, status}`，不记 prompt 正文 | 无法回答"哪个阶段最贵"，也无法应对客户数据合规审查 |

**为什么"不记 prompt 正文"**：汽车电子的图纸、BOM、客户规格书属于受控资料。审计只需要回答"谁、什么时候、花了多少"，不需要留存内容。留存正文会把网关变成新的数据泄露面。

**票据机制**（最小实现）：工单创建时网关签发 `ticket → opaque token`（仅内存 + 短期 TTL），执行器环境只有 `LLM_API_KEY=<opaque token>`。工单结束时吊销。这样即使执行器把 token 打印进日志，也只是一张过期即废的临时凭证。

## 7. 降级链与熔断

| 触发 | 网关动作 | 对工单的影响 |
| --- | --- | --- |
| 单 key 429 | 换池内下一把，退避 1s/2s/4s | 无感，延迟略升 |
| 池内全 429 | 排队（最多 60s），仍失败则向上报 `unavailable` | 研判：本轮不接单，下轮重试；执行器：`report(blocked)` |
| 单 key 5xx × 3 | 该 key 冷却 5 分钟 | 无感 |
| 主厂商整体不可用 | 切异构备厂商**同档位**模型 | 无感，但记录 `degraded` 事件 |
| 备厂商也只有弱档位 | **不降级**，`report(blocked)` | 等人决策：等待 / 手工处理 / 放宽要求 |
| 日预算超限 | 停止接新单（自动切 `observe`），在跑工单允许收尾 | 面板显示"预算熔断" |
| 单工单超预算 | 挂起该工单，保留现场 | 等人决定追加预算或拆单 |

注意最后两行是**两层预算**：日全局上限防系统性失控，单工单上限防个体跑飞。只做前者，一张问题工单就能吃掉全天额度。

## 8. 命名与配置规范

### 8.1 环境变量

```
EA_<ROLE>_<PROVIDER>_<NN>
```

| 示例 | 含义 |
| --- | --- |
| `EA_ROUTER_DS_01` | 研判池，厂商 A，第 1 把 |
| `EA_WORKER_DS_01` / `_02` | 执行器池主 key |
| `EA_WORKER_DS_03` | 执行器池热备 |
| `EA_WORKER_ALT_01` | 异构备厂商 |
| `EA_VISION_DS_01` | 多模态 |

规则：**只放环境变量名，不放值**；值来自密钥管理（Vault / KMS / 云厂商密钥服务），本地开发用 `keys.d/*.key`（`0600`，属主为 agent 账号，不入仓库、不入 `stateDir`）。

### 8.2 三层配置的归属

| 配置 | 放哪 | 为什么 |
| --- | --- | --- |
| key 的值 | 密钥管理 / `keys.d/` | 与代码、配置分离，可独立轮换 |
| 池与模型档位、限额、预算 | `config/ai-keys.example.yml`（网关读） | 变更不需要重启执行器 |
| `maxWorkers` 等机器限制 | `cordis.patch.yml` 的 `limits` | 与并发槽位一致，属机器级约束 |

**不要**把模型档位写进执行器预设。预设管的是"能用什么工具"，模型是"用哪个脑子"——两者变化频率不同，混在一起会导致每次换模型都要改预设并重启全部执行器。

### 8.3 MVP 阶段的落地（过渡形态，必须知道边界）

`mvp/` 目前**没有**本地网关，而是直连供应商的 OpenAI 兼容接口。这是刻意接受的过渡形态，不是遗漏：

| 项 | MVP 做法 | 与上文原则的关系 |
| --- | --- | --- |
| 密钥位置 | `~/.superagent/model.yml`（或环境变量 `SUPERAGENT_MODEL_*`，或 `model --file` 指定） | 满足"不进 Git、不进 `stateDir`、不进工单目录"三条硬规则；`~/.superagent/` 在主目录，根本进不了版本库 |
| 谁能用 | 只有一个进程、一个 key，无票据机制 | 单实例单用户场景下无意义；一旦多人共用就必须上网关 |
| 预算与换 key | 无 | 无网关就无法按工单熔断、无法失败换 key |
| 模型档位 | 单个 `model` 字段 | 无法区分研判 / 执行 / 文档 |

**迁移到网关的触发条件**（满足任意一条即应切换，而不是等"以后再说"）：

1. 用的人超过 1 个，或需要按人/项目归因；
2. 出现过因单张工单烧掉日额度而停摆；
3. 需要区分研判池与执行器池（一张大工单把研判卡住）；
4. 客户或审计要求提供 token 级审计。

在此之前，MVP 的 `model --check` 足以完成"这把 key 能不能用"的自检；配置文件模板见 [`mvp/model.example.yml`](../mvp/model.example.yml)。

**MVP 已实现的部分**（不必等网关）：岗位 → 池的映射、池内多 key 与"最久未失败优先"、按工单 token 熔断、按岗位/池的用量记账。也就是说，§3–§5 的"分池"思路已经在跑，缺的是网关那一层的**票据、密钥托管与金额换算**。

| 能力 | MVP | 网关 |
| --- | --- | --- |
| 分池（router/worker/doc/vision） | ✅ | ✅ |
| 池内多 key + 失败换 key | ✅ 进程内 | ✅ 跨进程 + 健康检查 |
| 按工单预算 | ✅ 按 token | ✅ 按金额 + 日/月配额 |
| 用量归因（岗位/池/工单） | ✅ SQLite | ✅ 时序库 + 报表 |
| 票据（随单签发/吊销） | ❌ | ✅ |
| 密钥托管（Vault/KMS） | ❌ 文件或环境变量 | ✅ |

**为什么不按"每个岗位一把 key"配**：岗位 5 个、调用形态 4 种。按岗位发 key 会得到 5 把低配额 key；一张工单跨 PM/HW/QE 三个岗位时，用量散落在 3 把 key 上，算不清单工单成本，限流时也无法把额度从空闲岗位挪给紧张岗位。正确做法是**岗位绑池、池内多 key**——表达力一样，配额可集中调度。

**管理入口**：MVP 提供 `/admin` 工作台，可看每个岗位的状态（在干活 / 空闲 / 无可用密钥）、今日用量、最近一次调用，以及每个池的密钥（掩码）、自检结果、累计用量；新增/停用/换 key/改预算后立即生效，不需重启。密钥存 `~/.superagent/keys.json`（0600），`model.yml` 保留为人工维护的基线。

## 9. 密钥生命周期

| 阶段 | 做法 |
| --- | --- |
| 生成 | 每把 key 对应厂商侧的**独立子账号或独立项目**，配额与告警可单独设；禁止多人共用一把 key 做别的事 |
| 分发 | 只写入密钥管理；网关启动时读取。人工不得通过聊天工具传递 |
| 轮换 | 90 天一次，新旧并存 7 天灰度（新 key 先接 10% 流量），观察 429 率与延迟后再切满 |
| 吊销 | 离职、外包结束、疑似泄露 → 立即吊销该 key，网关自动剔除，无需重启服务 |
| 审计 | 网关日志保留 180 天：`keyId`、`ticketId`、`role`、`stage`、token 数、状态码；不存正文 |

## 10. 成本归集与观测

按**四个维度**记账，才能回答真问题：

| 维度 | 能回答 | 用途 |
| --- | --- | --- |
| `projectId` | 哪个项目最贵 | 项目核算、报价 |
| `stage` | 哪个阶段最贵 | 通常 S3、S4 最高，可针对性优化模板 |
| `role` | 是研判贵还是执行贵 | 验证 2 节的比例假设是否成立 |
| `ticketId` | 哪类工单异常 | 发现"跑飞"的工单模式 |

面板需要四个数（其余都是噪音）：

1. 今日花费 / 预算水位；
2. 各 key 的 TPM 水位与 429 率；
3. 每张工单的平均成本与 p95；
4. 降级与熔断事件次数（理想为 0）。

**省钱的三个正解**（比换便宜模型有效得多）：

- **前缀缓存**：模板、分类规范、策略段是固定前缀，放在系统提示最前部，命中缓存可省 30–50% 输入 token；
- **模板结构化**：模板字段固定，输出可约束，减少来回返工——返工一次的代价远高于模型差价；
- **研判用小上下文**：只喂准入所需的元信息（发送者、群、首条消息、项目标签），不要把整个线程塞进研判。

## 11. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 所有角色共用一把 key | 研判被长任务饿死；限流互相踩踏 | 至少拆 `router` / `worker` 两池 |
| key 写进 `cordis.patch.yml` | 配置进 Git、进备份、进截图 | 配置只存环境变量名 |
| key 下发到执行器 env | 提示注入即可外带 | 本地网关 + 短期票据 |
| 按人发 key | 无法归因、无法回收、配额碎片化 | 按角色分池，按人分的是**权限**不是 key |
| 按阶段独立池 | 阶段并行度低，池子大量闲置 | 共享 `worker` 池，按 `stage` 打标签计费；仅在**合规等级不同**时才拆（如涉密图纸必须私有化端点） |
| 只做日预算不做单工单预算 | 一张工单吃光全天额度 | 两层预算都要 |
| 模型不可用时静默降级 | 质量文档注入弱模型输出，风险不可见 | `report(blocked)`，交人决策 |
| 用 RPM 估容量 | 低估 token 侧瓶颈，上线即 429 | 按 TPM 估算并留 30% 余量 |

## 12. 分阶段落地

| 阶段 | key 规模 | 网关 | 预算 | 目标 |
| --- | --- | --- | --- | --- |
| MVP（1–2 周） | 4（1 研判 / 2 执行 / 1 视觉） | 可先直连，但必须 env 注入、不得写配置 | 仅日上限 | 跑通一张 8D 工单 |
| 试点（4–6 周） | 7 | 引入网关：隔离 + 记账 + 换 key | 日上限 + 单工单上限 | 观察模式校准，成本可归因 |
| 生产（3 个月） | 10–12，含异构备厂商 | 网关 + 票据 + 熔断 + 审计 | 双层预算 + 熔断切 `observe` | 日 80 单，降级事件可解释 |
