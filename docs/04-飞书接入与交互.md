# 04 飞书接入与交互

## 1. 为什么只接飞书

原项目只监听一个 GitHub 仓库，本方案只监听一个飞书组织。单一信源带来三个确定性：

- **身份确定**：飞书 open_id 是唯一身份，准入表只需维护一份。
- **上下文确定**：话题（thread）天然对应"一个需求的完整讨论"。
- **回写确定**：答复回到原话题，不需要人再去别的系统找结果。

代价是无法覆盖邮件、供应商门户、PLM 审批。这些通过"人工搬运"解决：由有权限的人在飞书里重新发起，系统不直接对接。

## 2. 飞书应用配置

### 2.1 应用能力

| 项 | 配置 |
| --- | --- |
| 应用类型 | 企业自建应用 |
| 机器人 | 开启 |
| 事件订阅 | 长连接或 Webhook（推荐长连接，免公网入口） |
| 卡片回调 | 开启 `card.action.trigger` |
| 消息类型 | 文本、富文本、交互式卡片、文件 |

### 2.2 权限清单

| 权限 | 用途 |
| --- | --- |
| `im:message` | 发送消息 |
| `im:message.group_at_msg:readonly` | 读取群内 @ 机器人的消息 |
| `im:message.p2p_msg:readonly` | 读取单聊消息 |
| `im:chat:readonly` | 读取群信息 |
| `im:chat.members:readonly` | 读取群成员（用于准入同步） |
| `im:resource` | 读取消息中的图片与文件 |
| `contact:user.base:readonly` | 读取用户基本信息 |
| `drive:drive` | 归档文档到云空间（可选） |

### 2.3 事件订阅

| 事件 | 用途 |
| --- | --- |
| `im.message.receive_v1` | 接收消息 |
| `im.chat.member.user.added_v1` | 新成员入群，触发准入同步 |
| `card.action.trigger` | 卡片按钮回调 |

### 2.4 凭据隔离

与 `dsh-superagent` 一致，机器人凭据必须独立：

```sh
# 独立配置目录，避免与个人 lark-cli 冲突
LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-electronics" \
  lark-cli config init --app-id <cli_xxx> --app-secret-stdin

LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-electronics" \
  lark-cli config strict-mode bot --global

# 包装脚本
cat > ~/.local/bin/lark-electronics <<'EOF'
#!/bin/sh
export LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-electronics"
exec lark-cli "$@"
EOF
chmod +x ~/.local/bin/lark-electronics
```

**禁令**：机器人凭据不得具备用户身份能力；不得在聊天中传输 app secret。

## 3. 触发方式

### 3.1 支持的触发

| 方式 | 说明 | 授权强度 |
| --- | --- | --- |
| 群内 @ 机器人 + 文本 | 主入口 | explicit |
| 群内话题回复（已订阅） | 补充上下文 | inferred |
| 单聊机器人 | 私密需求 | explicit |
| 卡片提交 | 结构化表单 | explicit |
| 卡片按钮 | 确认/退回/放行 | 按角色判定 |

### 3.2 不支持的触发

- 编辑历史消息追加 @（飞书不推送编辑事件）；
- 机器人消息（除白名单机器人）；
- 未 @ 的群消息（除非群设置为"接收全部消息"且策略允许）；
- 外部群、外部联系人。

## 4. Trigger 翻译规则

飞书原始事件 → 领域 Trigger 的映射：

| 领域字段 | 来源 | 说明 |
| --- | --- | --- |
| `id` | `feishu:<message_id>` | 幂等键，重复投递直接忽略 |
| `source` | `feishu` | 固定 |
| `threadKey` | `chat_id:root_message_id` | 话题根消息；非话题群用首条消息 |
| `actor.id` | `sender.open_id` | 唯一身份 |
| `actor.name` | `sender.name` | 展示用 |
| `text` | 消息正文（去除 @） | 纯文本化 |
| `attachments` | 图片/文件 key | 延迟下载 |
| `addressed` | `mention` / `direct` / `none` | 是否点名机器人 |
| `projectId` | 群绑定或消息标签 | 用于准入与路由 |
| `at` | 事件时间 | 排序用 |
| `raw` | 原始 JSON | 审计用 |

### 4.1 Thread 定义

- **话题群**：`chat_id + root_message_id`。
- **普通群**：`chat_id + 当日日期`，避免整个群变成一条线程。
- **单聊**：`p2p:<open_id>`。

一个 Thread 同时只允许一个 Eval 运行；期间到达的消息合并进下一批。

### 4.2 幂等与去重

```
if exists(trigger.id): return duplicate
store(trigger)
```

飞书可能重复推送同一事件，幂等键必须在入库前检查。

## 5. 交互卡片设计

卡片是结构化输入的主要手段，避免自由文本带来的歧义。

### 5.1 需求提交卡片

```
┌──────────────────────────────────────┐
│ 提交工程需求                          │
├──────────────────────────────────────┤
│ 项目      [PCU24 ▾]                  │
│ 任务类型  [设计变更 ▾]                │
│ 严重度    [中 ▾]                      │
│ 需求描述  [____________________]      │
│ 关联需求  [REQ-____]                  │
│ 期望节点  [2026-12-15]                │
│         [取消]  [提交]                │
└──────────────────────────────────────┘
```

提交后回调返回 `trigger`，进入正常准入流程。

### 5.2 阶段门确认卡片

```
┌──────────────────────────────────────┐
│ G2 设计冻结评审 · 待签署              │
├──────────────────────────────────────┤
│ 交付物 6/6 齐套                       │
│ 自动检查 通过 4 项，警告 1 项          │
│ ⚠ DFMEA 高风险项 RPN>100 共 2 条      │
│ 详见：[查看证据包]                    │
│      [退回]  [签署放行]               │
└──────────────────────────────────────┘
```

按钮回调校验签署人角色与授权，通过后写入门禁记录。

### 5.3 问题澄清卡片

执行器需要人决策时，只问一个问题：

```
┌──────────────────────────────────────┐
│ 需要你的决定                          │
├──────────────────────────────────────┤
│ 问题：该变更是否影响已交付的 hw-1.1？  │
│ ○ 影响，需要客户通知                  │
│ ○ 不影响，仅内部变更                  │
│ ○ 不确定，转质量部评估                │
└──────────────────────────────────────┘
```

### 5.4 结果通知卡片

```
┌──────────────────────────────────────┐
│ 工单 TKT-2026-0031 已完成             │
├──────────────────────────────────────┤
│ 产出：                                │
│ · ECN 变更通知 v1.0                   │
│ · DFMEA 更新（3 条）                  │
│ · PR #128（待评审）                   │
│ 下一步：等待代码评审                   │
└──────────────────────────────────────┘
```

## 6. 消息策略

严格遵循"只在必须时说话"。

| 场景 | 是否发言 | 内容长度 |
| --- | --- | --- |
| 接单确认 | 是，一次 | ≤ 30 字，说明将做什么 |
| 执行中 | 否 | — |
| 需要决策 | 是 | 一个问题 + 选项 |
| 完成 | 是 | 结果 + 链接 |
| 失败 | 是 | 原因 + 已尝试 + 建议 |
| 阶段门待签署 | 是 | 证据摘要 + 签署入口 |
| 超时提醒 | 是，最多两次 | 一行 |
| 健康状态 | 否 | 面板可见即可 |

**硬限制**：

- 单条消息 ≤ 100 字（卡片除外）；
- 同一工单同一状态不重复通知；
- 夜间（22:00–08:00）非紧急消息静默，次日 09:00 汇总；
- 不使用 @所有人。

## 7. 回写通道

| 通道 | 用途 | 失败处理 |
| --- | --- | --- |
| 飞书话题回复 | 主通道，答复与通知 | 重试 3 次，失败转私聊，再失败记问题 |
| 仓库 PR | 代码与文档变更 | 失败则重试；分支保留 |
| 文档库（云空间） | 归档正式文档 | 失败则暂存本地并登记待同步 |

**通道降级顺序**：话题 → 私聊 → 面板待办。任何降级都要在面板留痕。

## 8. 准入表

飞书侧的准入由三张表构成。

### 8.1 人员白名单

| open_id | 姓名 | 角色 | 可发起 | 可签署 |
| --- | --- | --- | --- | --- |
| ou_xxx1 | 张工 | 硬件工程师 | 设计变更、文档 | 否 |
| ou_xxx2 | 李工 | 质量工程师 | 质量问题、8D | G3/G4 |
| ou_xxx3 | 王经理 | 项目经理 | 立项、变更 | G1/G2 |

### 8.2 群准入

| chat_id | 群名 | 项目 | 接收模式 | 允许类型 |
| --- | --- | --- | --- | --- |
| oc_aaa | PCU24 研发群 | PCU24 | 仅 @ | 全部 |
| oc_bbb | 质量问题群 | PCU24 | 仅 @ | 质量问题 |
| oc_ccc | 供应商质量群 | 多项目 | 仅 @ | 质量问题 |

### 8.3 单元格策略

每个群可配置三种情况的处理：

| 情况 | 选项 | 默认 |
| --- | --- | --- |
| 白名单成员、未 @ | 推断 / 忽略 | 推断 |
| 非白名单、@ 了 | 明确 / 推断 / 忽略 | 忽略 |
| 非白名单、未 @ | 推断 / 忽略 | 忽略 |

## 9. 飞书 Source 的失败模式

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| @ 了没反应 | 发送者不在白名单 / 群未开启 / 处理已暂停 | 面板检查三处 |
| 消息重复处理 | 幂等键失效 | 检查 message_id 是否被改写 |
| 卡片按钮无响应 | 回调地址未配置 / 签名校验失败 | 查看应用日志 |
| 机器人不在群 | 被移出 | 重新拉入群 |
| 读取成员失败 | 权限不足 | 补 `im:chat.members:readonly` |
| 文件下载失败 | 资源权限不足 | 补 `im:resource` |

## 10. 与 dsh-superagent 的对应

| 本方案 | dsh-superagent |
| --- | --- |
| 飞书事件适配器 | GitHub Source |
| 话题 = Thread | Issue = Thread |
| 卡片提交 | 评论 @ |
| 卡片按钮回调 | 面板操作 |
| 三通道回写 | GitHub 评论 + PR |
| 群准入表 | Source 准入表 |
