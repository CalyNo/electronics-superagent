# 02 IATF 16949 流程编排

## 1. 流程总览

本方案以 **APQP 五阶段**为骨架，以**阶段门（Gate）**为控制点，把飞书进来的每一条需求映射为一个阶段化任务流。

```
需求进入
   │
   ▼
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ S1 策划 │──▶│ S2 产品 │──▶│ S3 过程 │──▶│ S4 验证 │──▶│ S5 量产 │
│         │ G1│  设计   │ G2│  设计   │ G3│         │ G4│  准备   │
└─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
     │             │             │             │             │
     └─────────────┴─────────────┴─────────────┴─────────────┘
                          持续：变更管理 / 问题解决 / 追溯
```

每个 `G` 是阶段门：上一阶段的交付物齐套且通过校验，人签署后方可进入下一阶段。

## 2. 阶段定义与交付物

### 2.1 S1 计划和确定项目

| 项 | 内容 |
| --- | --- |
| 目的 | 确认需求可行、资源到位、计划可执行 |
| 输入 | 客户需求、RFQ、法规要求、历史项目经验 |
| 关键活动 | 可行性分析、团队组建、进度与成本估算、初始特殊特性识别 |
| 交付物 | 项目章程、需求规格书、APQP 项目计划、可行性分析、团队与职责矩阵、风险登记册 |
| 阶段门 G1 | 立项评审：需求清晰、资源承诺、计划批准 |
| 电子行业补充 | 关键元器件长周期件识别、AEC-Q 认证需求确认、EMC/安规目标确认 |

### 2.2 S2 产品设计和开发

| 项 | 内容 |
| --- | --- |
| 目的 | 完成硬件与软件设计，识别并降低设计风险 |
| 输入 | 已批准的 S1 交付物 |
| 关键活动 | 方案设计、原理图/PCB、DFMEA、设计验证计划（DVP）、特殊特性确定、软件架构 |
| 交付物 | 设计规格书、DFMEA、DVP&R、特殊特性清单、原理图、PCB、软件架构文档、设计评审记录 |
| 阶段门 G2 | 设计冻结评审：DFMEA 高风险项有措施、DVP 覆盖全部特殊特性、设计评审闭环 |
| 电子行业补充 | EVT 样机验证、元器件降额分析、热仿真、信号完整性、功能安全（如适用） |

### 2.3 S3 过程设计和开发

| 项 | 内容 |
| --- | --- |
| 目的 | 设计可稳定制造的过程，识别并控制过程风险 |
| 输入 | 已冻结的设计、制造可行性 |
| 关键活动 | 过程流程图、PFMEA、控制计划、工装与检具设计、作业指导书、包装规范 |
| 交付物 | 过程流程图、PFMEA、控制计划、工装清单、作业指导书、检验规范、包装规范 |
| 阶段门 G3 | 过程准备评审：PFMEA 与流程图一致、控制计划覆盖特殊特性、工装就绪 |
| 电子行业补充 | SMT 工艺参数、ICT/FCT 测试方案、AOI 程序、防静电（ESD）控制、洁净度要求 |

### 2.4 S4 产品和过程确认

| 项 | 内容 |
| --- | --- |
| 目的 | 用数据证明产品与过程满足要求 |
| 输入 | 已就绪的过程、试产计划 |
| 关键活动 | 试生产、MSA、初始过程能力研究、尺寸/材料/性能试验、可靠性试验、PPAP 准备 |
| 交付物 | 试产报告、MSA 报告、SPC/过程能力报告、尺寸报告、材料与性能报告、可靠性报告、PPAP 提交包 |
| 阶段门 G4 | PPAP 批准：18 项要素齐套、过程能力达标、客户批准 |
| 电子行业补充 | AEC-Q100/Q101 测试报告、EMC 测试、环境试验（温循/湿热/振动/盐雾）、寿命试验 |

### 2.5 S5 反馈、评定和纠正措施

| 项 | 内容 |
| --- | --- |
| 目的 | 量产稳定、持续改进、变更受控 |
| 输入 | 量产数据、客户反馈、审核发现 |
| 关键活动 | 量产监控、SPC 日常监控、变更管理（ECR/ECN）、8D 问题解决、经验教训固化 |
| 交付物 | 量产监控报告、变更记录、8D 报告、经验教训库、年度改进计划 |
| 阶段门 G5 | 量产放行后进入持续监控，无固定终点；重大变更需重新走 G2–G4 |
| 电子行业补充 | 批次追溯、失效分析（FA）、供应商质量（SQE）联动、召回预案 |

## 3. 任务类型与自动路由

飞书消息进入后，研判器（Assessment）先判定任务类型，再决定走哪条编排路径。

| 任务类型 | 典型触发语 | 起始阶段 | 默认交付物 | 是否需要阶段门 |
| --- | --- | --- | --- | --- |
| 新项目立项 | "启动 XX 项目" | S1 | 章程、需求规格、APQP 计划 | 是（G1） |
| 设计变更 | "把 XX 改成 YY" | S2 | ECN、DFMEA 更新、DVP 更新 | 是（G2） |
| 过程变更 | "换一条 SMT 线" | S3 | ECN、PFMEA 更新、控制计划更新 | 是（G3） |
| 质量问题 | "客户投诉 XX 失效" | S5 | 8D、FA 报告、纠正措施 | 否（走 8D 时限） |
| 文档补齐 | "补一份 DFMEA" | 当前阶段 | 对应模板文档 | 视阶段而定 |
| 验证任务 | "跑一轮温循" | S4 | 测试计划、测试报告 | 否 |
| 仓库维护 | "把 BOM 更新到最新" | 任意 | 提交 + PR | 否 |

### 3.1 路由判定规则（供 Assessment 使用）

```
输入：消息文本、项目标签、发送者角色、线程历史
输出：taskType、startStage、gateTarget、requiredTemplates、riskLevel

规则优先级（自上而下，命中即停）：
1. 含"投诉/失效/退货/客诉" → 质量问题，startStage=S5
2. 含"变更/ECN/替换/改版"   → 设计或过程变更，按影响面判定
3. 含"立项/新项目/开发"      → 新项目，startStage=S1
4. 含"测试/试验/验证"        → 验证任务，startStage=S4
5. 含"补/完善/更新文档"      → 文档补齐，startStage=当前阶段
6. 其它                      → 需人工澄清（抛出一个结构化问题）
```

**风险分级**：

| 等级 | 判定 | 处理 |
| --- | --- | --- |
| 高 | 涉及安全件、法规件、客户特殊特性 | 必须 G 门签署 + 质量负责人复核 |
| 中 | 涉及特殊特性但非安全件 | G 门签署 |
| 低 | 一般文档、注释、非功能改动 | 执行器自检 + 同行评审 |

## 4. 阶段门规则

### 4.1 门禁检查项

每个阶段门由三类检查构成：

| 类型 | 执行者 | 示例 |
| --- | --- | --- |
| 自动完整性检查 | 系统 | 交付物清单是否齐套；模板字段是否完整；DFMEA 高风险项是否都有措施 |
| 自动一致性检查 | 系统 | 过程流程图工序与 PFMEA 条目是否一一对应；控制计划是否覆盖全部特殊特性 |
| 人工签署 | 责任人 | 设计冻结、PPAP 批准、变更批准 |

### 4.2 门禁不通过的处理

- **自动检查失败**：工单置为 `blocked`，在飞书原话题抛出一个具体问题（缺哪个文件、缺哪个字段、哪条不一致）。
- **人工退回**：工单置为 `blocked`，记录退回原因，执行器按原因修订后重新提交。
- **超时未签署**：按策略配置提醒责任人，超过阈值升级至上级。

### 4.3 门禁与工单状态映射

| 门禁状态 | 工单状态 | 执行器可做 |
| --- | --- | --- |
| 未开始 | 已接单 | 准备阶段资料 |
| 准备中 | 执行中 | 生成文档、改代码 |
| 待签署 | 待评审 | 只读，等待人 |
| 已放行 | 已关闭（阶段完成） | 进入下一阶段 |
| 已退回 | 阻塞 | 按退回原因修订 |

## 6. 变更管理（ECN）

变更不是"重新走一遍流程"，而是**在既有基线上做受控增量**。

### 6.1 变更分级

| 等级 | 判定 | 审批 | 需重新验证 |
| --- | --- | --- | --- |
| 重大 | 影响安全/法规/客户特殊特性/接口 | 变更委员会 + 客户 | 全项 DVP + PPAP |
| 一般 | 影响性能但不影响接口 | 变更委员会 | 相关项 DVP |
| 微小 | 文档、注释、不影响功能 | 技术负责人 | 自检 |

### 6.2 变更流程

```
ECR 提出 → 影响分析 → 变更评审 → ECN 批准 → 实施 → 验证 → 基线更新 → 追溯登记
```

系统自动完成：

- 生成 ECR/ECN 草稿并套模板；
- 检索受影响的文档（通过追溯矩阵反查）；
- 生成影响清单：哪些 DFMEA 条目、PFMEA 条目、控制计划、测试用例需更新；
- 创建变更分支与 PR；
- 更新版本号与追溯矩阵。

系统不做：

- 变更批准（人）；
- 客户沟通（人，系统只准备材料）；
- 基线冻结（人）。

## 7. 问题解决（8D）

质量问题走独立的 8D 时限管理，不套 APQP 阶段门。

| 阶段 | 时限（默认） | 系统动作 |
| --- | --- | --- |
| D1 成立小组 | 24h | 生成小组名单与职责 |
| D2 描述问题 | 48h | 套模板，要求 5W2H + 照片/数据 |
| D3 临时措施 | 72h | 检查是否覆盖在制品与库存 |
| D4 根因分析 | 7d | 提示使用 5Why/鱼骨图，要求证据 |
| D5 永久措施 | 14d | 关联 ECN（如需变更） |
| D6 验证 | 21d | 要求验证数据 |
| D7 预防再发 | 28d | 检查是否更新 FMEA/控制计划 |
| D8 结案 | 30d | 汇总并登记经验教训 |

超时自动提醒，并在面板高亮。

## 10. 实施注意

1. **先固化模板，再谈自动化**。模板不稳定时，自动生成的文档会反复返工。
2. **阶段门先人工、后半自动**。前三个月由人逐项检查，同时记录检查项，之后再把确定性检查交给系统。
3. **变更流程比新项目流程更常用**。优先把 ECN 跑通，收益最直接。
4. **8D 是最容易见效的切入点**。结构固定、时限明确、痛点集中，适合作为 MVP 的第一个场景。
