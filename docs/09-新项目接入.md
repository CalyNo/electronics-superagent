# 09 新项目接入

> 本文回答两个问题：**新项目导入时生成什么样的 Git 仓库**、**执行器在什么样的工作目录里干活**。
> 稳定态的仓库结构见 [03-资产分类规范](03-资产分类规范.md)；本文只定义从零到第一次可接单之间的动作。

## 1. 先判定接入形态

"新项目"在汽车电子里通常有三种含义，对应的仓库结构完全不同。**判定错了，后面所有规则都要重写**，所以这一步必须由项目负责人与平台负责人共同确认并记录。

| 形态 | 判定标准 | 仓库 | 默认 |
| --- | --- | --- | --- |
| **A 独立仓库** | 独立 BOM、独立发布节奏、独立客户或独立产线 | 新建 `<code>` 仓库 | ✅ 默认 |
| **B 同仓命名空间** | 同平台衍生型号：共享主板/BSP，仅配置、标定、外设增减不同 | 在既有仓库新增 `projects/<CODE>/` | 满足条件时 |
| **C 多仓分离** | 团队 > 30 人，或硬件与软件权限/节奏差异大 | `<code>-docs` / `-firmware` / `-hardware` | 仅大团队 |

**为什么默认 A 而不是 B**：单仓多目录的成本随项目数线性上升——LFS 配额叠加、clone 时间叠加、权限粒度被迫放大。而汽车电子的跨项目引用通常只发生在同一平台内部，一旦跨平台，"共享"往往是伪需求。宁可先建仓，等到第二个变型型号出现时再合并，也不要一开始就为不存在的复用付代价。

**形态 B 的代价**（必须提前接受）：

- 03 文档的仓库骨架要整体下沉一层到 `projects/<CODE>/`；
- 执行器的写权限必须限定到 `projects/<CODE>/`，否则一个项目的工单能改另一个项目的文档；
- 追溯矩阵需要区分"项目内引用"与"平台引用"两类边。

## 2. 生成什么：形态 A 的仓库骨架

以项目代号 `PCU24`（电机控制器 2024 平台）为例，`new-project.sh` 生成如下结构：

```
pcu24/                                  # 仓库名 = 项目代号小写
├── .gitattributes                      # LFS 规则
├── .gitignore
├── README.md                           # 项目身份、责任人、当前阶段、门禁状态
├── .github/
│   ├── CODEOWNERS                      # 按阶段目录分配评审人
│   └── pull_request_template.md        # 与 05 §3.3 一致
├── .superagent/                        # 系统读的项目配置（人可读，人不可随意改）
│   ├── manifest.yml                    # 项目身份与能力开关
│   ├── rules.yml                       # 项目级规则覆盖
│   └── taxonomy.yml                    # 分类扩展（项目专属类型）
├── docs/
│   ├── _templates/                     # 平台模板副本，只读，随平台升级
│   ├── _index/
│   │   ├── documents.csv               # 文档索引
│   │   ├── traceability.csv            # 追溯矩阵
│   │   └── import-map.csv              # 仅存量导入项目存在
│   ├── S1-策划/{CHTR,SRS,APQP,FEAS}/
│   ├── S2-产品设计/{DFMEA,DVP,SC}/
│   ├── S3-过程设计/{PFC,PFMEA,CP}/
│   ├── S4-验证/{MSA,SPC,TR,PPAP}/
│   ├── S5-量产/{8D,ECN}/
│   ├── _common/{MIN,REV,RISK}/         # 跨阶段通用文档
│   └── _archive/                       # 作废与历史版本
├── hardware/
│   ├── bom/  schematic/  pcb/  mechanical/  fixture/  datasheet/
│   ├── manifest.yml                    # 硬件资料哈希清单（03 §5.3）
│   └── _released/
│       └── compatibility.yml           # 硬件-固件兼容矩阵（03 §4.5）
├── firmware/{app,drivers,bsp,bootloader,config}/
├── software/{gui,tools}/
├── test/{unit,hil}/
├── evidence/                           # 已提交的验证证据，按工单号分目录
└── tools/
    ├── validators/                     # front-matter / manifest / 追溯校验
    └── generators/
```

### 2.1 两个容易混淆的 `evidence`

| 位置 | 性质 | 是否进 Git | 保留 |
| --- | --- | --- | --- |
| `<stateDir>/work/<TICKET>/evidence/` | 执行过程中的原始日志、截图、临时测量数据 | 否 | 工单结束后 7 天随工作目录清理 |
| `<repo>/evidence/<TICKET>/` | 经筛选、作为 PPAP 或 8D 证据提交的定稿材料 | 是 | 按记录保存年限（默认 15 年） |

规则：**工作目录里的证据可以丢，仓库里的证据不能丢**。执行器在 `report(ready)` 前必须把要长期留存的证据复制进仓库并登记索引，否则 PPAP 阶段会拿不出证据链。

### 2.2 空目录如何进 Git

Git 不跟踪空目录。生成器在创建的空目录放 `.gitkeep`，使骨架能随仓库同步；但**未启用的阶段完全不创建**——阶段目录按 `manifest.yml` 的 `stages.enabled` 生成，尚在 S1 的项目不会有 `S4-验证/`、`S5-量产/`，避免一堆永远为空的占位目录把面板的齐套率分母抬高。

## 3. 形态 B 的仓库骨架

```
pcu-platform/                           # 平台仓
├── README.md                           # 平台说明 + 项目清单
├── .gitattributes  .gitignore  .github/    # 仓库级，与形态 A 相同
├── platform/                           # 共享资产，执行器默认只读
│   ├── bsp/  drivers/
│   ├── hardware/{schematic,pcb}/       # 主板原理图与 PCB
│   └── docs/                           # 平台级规范
├── projects/
│   ├── PCU24/                          # 与形态 A 完全相同的子树
│   │   ├── README.md
│   │   ├── .superagent/                # 项目级配置（每个项目一套）
│   │   ├── docs/  hardware/  firmware/  software/  test/  evidence/  tools/
│   └── PCU24S/
└── docs/_index/                        # 全局索引，含跨项目追溯边
```

注意 `projects/<CODE>/` 内部结构就是形态 A 的整棵树，**项目级配置跟着项目走**，不去仓库根抢位置。仓库根只放真正跨项目的东西：LFS 规则、CODEOWNERS、全局索引、平台说明。

关键约束：执行器预设的 `writeRoots` 必须是 `projects/<CODE>/`，`platform/` 只读。**否则 A 项目的工单可以改 B 项目的 DFMEA**——这类事故在评审时极难发现，因为 diff 看起来完全正常。

## 4. `.superagent/` 三个文件

这三个文件是"系统能自动干活"的前提，必须在基线冻结前填写完整。字段定义见 `scaffold/.superagent/*.yml`，此处说明职责边界。

| 文件 | 回答什么 | 谁维护 | 改动影响 |
| --- | --- | --- | --- |
| `manifest.yml` | 这个项目是什么、启用了哪些阶段、责任人是谁、记录保存多久 | 项目负责人 | 改动需新工单；`code` 永不可改 |
| `rules.yml` | 本项目对全局规则的**加严**（不可放宽） | 质量 + 平台 | 立即生效，向在跑工单发策略变更通知 |
| `taxonomy.yml` | 项目专属文档类型、命名例外、路径映射 | 平台 | 改动需重建索引 |

**`rules.yml` 只能加严，不能放宽**——这是防止"某个项目嫌流程麻烦就自己关掉门禁"的关键设计。放宽只能改平台级 `policy.example.yml`，走质量部门审批。校验器在启动时比对：若项目规则弱于平台基线，直接拒绝启动并在面板报错。

## 5. Git 仓库初始化

### 5.1 分支与基线

```sh
git init -b main
# 生成骨架 → 首次提交由人完成（执行器不得创建基线）
git add -A && git commit -m "chore(bootstrap): PCU24 项目骨架与模板基线"
git branch develop
git tag -a baseline-v0.0.1 -m "PCU24 骨架基线，可供智能体接单"
git push -u origin main develop --tags
```

`baseline-v0.0.1` 是**授权起点**：工单的 `Mandate` 记录基线 tag，任何提交都能反查到"从哪个基线开始改的"。没有基线的仓库不允许接单——否则第一张工单的 diff 会混入整套骨架，评审无法进行。

### 5.2 保护规则（必须在首张工单前配置好）

| 规则 | `main` | `develop` | `agent/*` `feature/*` `change/*` `fix/*` |
| --- | --- | --- | --- |
| 禁止直推 | ✅ | ✅ | ❌ 允许执行器推送 |
| 必须 PR | ✅ | ✅ | 可选 |
| 最少评审人数 | 2 | 1 | 0 |
| CODEOWNERS 强制 | ✅ | ✅ | ❌ |
| 状态检查（CI 校验器） | ✅ | ✅ | ✅ |
| 禁止 force push | ✅ | ✅ | ✅ |
| 禁止删除分支 | ✅ | ✅ | ❌ 允许系统清理 |
| 要求线性历史 | ✅ | ✅ | ❌ |

执行器账号以 **collaborator（write）** 身份加入，并单独建 `agents` 组——不要给它 admin，也不要用个人账号代跑。

### 5.3 LFS 与忽略规则

`.gitattributes` 必须覆盖硬件二进制，否则第一次提交原理图就会把仓库撑爆：

```
*.SchDoc  filter=lfs diff=lfs merge=lfs -text
*.PcbDoc  filter=lfs diff=lfs merge=lfs -text
*.GBR     filter=lfs diff=lfs merge=lfs -text
*.zip     filter=lfs diff=lfs merge=lfs -text
*.step    filter=lfs diff=lfs merge=lfs -text
*.stp     filter=lfs diff=lfs merge=lfs -text
*.xlsx    filter=lfs diff=lfs merge=lfs -text
*.pdf     filter=lfs diff=lfs merge=lfs -text
```

`.gitignore` 需要排除的不是"构建产物"那么笼统，而是三类具体东西：编译中间件（`firmware/**/build/`、`*.o`）、工装临时数据（`test/hil/runs/`）、密钥与本地配置（`*.key`、`.env*`、`local.yml`）。

## 6. 运行时工作目录

仓库是**持久资产**，工作目录是**一次性现场**。两者不能混。

```
/srv/superagent/state/pcu24/            # stateDir，与仓库一对一
├── orchestrator.sqlite                 # 工单、授权、决策、审计（升级前必备份）
├── orchestrator.lock
├── work/
│   └── TKT-2026-0031/                  # 每个工单一个目录
│       ├── repo/                       # git worktree，指向 agent/TKT-2026-0031
│       ├── inputs/                     # 飞书附件、截图、客户资料
│       ├── outputs/                    # 中间产物（草稿、计算表）
│       ├── evidence/                   # 临时证据（测试日志、截图）
│       └── .ticket.json                # 工单元数据：授权、基线、预算、阶段
├── worker-bin/                         # gh / lark-cli 垫片（PATH 首位）
├── worker-gitconfig/                   # 替换全局 git 配置，剥离凭据
├── artifacts/                          # 运行日志，保留 20 份
└── control/                            # 停止标记、profile 控制文件
```

**stateDir 与仓库一对一**，因为 [01-总体设计](01-总体设计.md) 规定一个实例只服务一个产品线。要在一台机器上跑三个项目，就是三个 stateDir、三个 profile、三个 systemd/tmux 会话，各自独立启停与升级——这比"一个实例管多项目"简单得多，代价只是多占一点内存。

`work/<TICKET>/repository` 用 `git worktree` 而非 `clone`：多个工单共享同一份对象库，几百 MB 的硬件历史不会被复制 N 遍。工单结束保留 7 天用于追溯，之后由清理任务删除，**但 `.ticket.json` 与最终 PR 链接会归档进数据库**，所以清理不丢审计线索。

## 7. 导入流程（七步）

| 步 | 动作 | 谁做 | 产出 | 验收 |
| --- | --- | --- | --- | --- |
| 0 | 定项目代号 | 项目负责人 | `PCU24`（2–8 位大写字母数字，终身不变，不复用） | 与既有项目无冲突 |
| 1 | 判定形态 A/B/C | 负责人 + 平台 | 决策记录（写进 `manifest.yml` 的 `topology`） | 三条判定标准逐条勾选 |
| 2 | 建仓 + 保护规则 | 平台 | 空仓、分支、保护、agent 账号 | 试推 `main` 必须被拒 |
| 3 | 生成骨架 | 平台 | `new-project.sh` 输出 | `--verify` 全绿 |
| 4 | 平台注册 | 平台 | profile、stateDir、source、policy 中的项目条目 | 面板显示 source ready |
| 5 | 存量资产导入 | 项目 + 平台 | `import-map.csv` + 索引 | 抽样 20 份可反查 |
| 6 | 基线冻结 | 项目负责人（人） | `baseline-v0.0.1` tag | CI 校验器通过 |
| 7 | 试运行 | 平台 | 一张真实工单走完 | `observe` 模式 2 周，再评估切 `auto` |

### 7.1 存量项目导入的三条铁律

大部分团队不是从零开始，而是把已有项目搬进来。完整的七步流程、四种接入形态、分类映射与回滚方案见 [10-存量项目迁移](10-存量项目迁移.md)，这里只列不可让步的三条：

1. **不改名、不移动**。03 §3.3 规定"文件名一旦发布不得改名"，这条对存量同样有效。强行改名会让历史评审记录、客户提交件、体系文件里的引用全部失效。
2. **用映射表，不用目录迁移**。`docs/_index/import-map.csv` 记录 `旧路径 → 资产ID → 类型 → 阶段`，追溯矩阵一律引用资产 ID 而非路径。这样物理位置可以慢慢整理，追溯链先建起来。
3. **不能补 front-matter 的，加 sidecar**。PDF、Word、客户图纸改不了元数据，就在旁边放 `<原名>.meta.yml`，内容与 front-matter 同构。改原文件是下策——会破坏哈希与客户提交件的对版关系。

```csv
oldPath,assetId,type,stage,status,note
03_设计输出/DFMEA_电机控制器_v2.3.xlsx,DOC-S2-DFMEA-001,DFMEA,S2,released,客户已批准，保持原名
02_需求/客户SOR_2024.pdf,DOC-S1-SRS-001,SRS,S1,released,sidecar 元数据
```

## 8. 验收清单

新项目生成后，逐项确认（前六项可由脚本检查，后三项必须人工）：

- [ ] 目录骨架与 `manifest.yml` 的 `stages.enabled` 一致，无多余阶段目录
- [ ] `.superagent/` 三文件必填字段齐全，`code` 与仓库名一致
- [ ] `.gitattributes` 覆盖全部硬件二进制后缀，`git lfs ls-files` 可验证
- [ ] `main`/`develop` 保护生效：试推被拒、缺评审无法合并
- [ ] `baseline-v0.0.1` tag 存在且指向初始提交
- [ ] `tools/validators` 在空仓库上跑通（无文档时应为"通过"而非报错）
- [ ] `rules.yml` 未弱于平台基线（校验器已拒绝启动即视为通过）
- [ ] CODEOWNERS 中每个阶段目录都有真实责任人，不是占位符
- [ ] 项目在 Policy 的 `allowed` 项目列表中存在，白名单成员可发起工单

## 9. 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 让执行器创建初始提交 | 基线混入智能体生成内容，责任边界模糊 | 首提必须由人完成并签名 |
| 未建 develop 直接让执行器推 main | 保护规则缺失，第一张工单就污染量产基线 | 先配保护再开单 |
| 为"以后可能用到"建全五阶段目录 | 齐套率统计分母虚高，面板长期标红 | 按 `stages.enabled` 生成 |
| 存量文件批量改名对齐编号 | 客户提交件与体系文件引用断裂 | 用 `import-map.csv` |
| 三个项目共用一个 stateDir | 数据库锁互斥、工单串项目、预算无法归集 | 一项目一 stateDir |
| 跳过基线 tag 直接接单 | 首张工单 diff 含整套骨架，评审不可行 | 先冻结基线 |
