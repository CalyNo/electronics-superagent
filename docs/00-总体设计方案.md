# 00 总体设计方案

> 本文是**工程蓝图**：把 `01`–`10` 的业务设计收敛为可编码的架构、接口与数据结构，并界定 MVP 边界。
> 角色分工：`01` 讲为什么这样设计，`02`–`06` 讲业务规则，`09`–`10` 讲接入与迁移，**本文讲怎么实现**，`mvp/` 是本文的可运行实例。

## 1. 设计基线

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 运行时 | Node.js ≥ 22.5（实测 22.22） | 需要内置 `node:sqlite`，免编译依赖 |
| 第三方依赖 | **零** | 客户内网常无 npm 源；零依赖使 `git clone` 即可运行 |
| 持久化 | 单文件 SQLite（WAL） | 单实例单写入者，事务即一致性边界 |
| 执行模型 | 单进程 + 协作式调度 | MVP 不引入队列中间件；执行器串行，避免并发写仓库 |
| 信息源 | 单源（本地文件 / 飞书二选一） | 与 `01` §1.1 非目标一致 |
| 仓库 | 单仓多目录（拓扑 A） | 与 `09` §5 一致 |

**不引入的东西**（都有明确理由，不是遗漏）：消息队列、ORM、Web 框架、状态机库、模板引擎、YAML 第三方库、LLM SDK。前四个各只用到 5% 的能力，后三个替换成本低于引入成本。

## 2. 范围界定

### 2.1 MVP 做什么

一条完整闭环，可从飞书（或本地目录）发起，到仓库里出现受控产物：

1. **接入**：消息 → Trigger（幂等、去重、丢弃机器人自身消息）
2. **准入**：身份 + 群准入表 → 明确 / 推断 / 拒绝
3. **研判**：关键词路由 → 任务类型、起始阶段、交付物清单、风险等级
4. **授权**：Ticket + 不可变 Mandate（仓库范围、阶段范围、动作范围）
5. **执行**：套模板生成文档 → 结构校验 → 资产分类落位 → Git 分支与提交 → PR 草案
6. **门禁**：自动化检查（齐套、结构、OP 一致性、特殊特性覆盖）→ `待签署`
7. **签署**：仅人可操作；系统记录签署人与时间
8. **回写**：飞书话题回复（本地模式写 outbox 文件）
9. **观测**：面板看"需要我做什么 / 系统健康 / 一件事的完整历史"

### 2.2 MVP 不做什么（且不做假实现）

| 不做 | 原因 | 替代 |
| --- | --- | --- |
| 真实 LLM 生成技术内容 | MVP 无密钥与网关；编造 DFMEA 结论比不生成更有害 | 生成**结构化骨架 + 待确认标记**，内容由人填；网关接口留好 |
| 独立执行器会话/沙箱 | 需要 DSH 或容器编排 | 进程内执行器，但**边界照留**（工具白名单、目录隔离、禁止改配置） |
| 自动合并 PR / 打标签 | 违反 `01` §6 最小权限 | 只出 PR 草案；合并与打标签走人 |
| 多源聚合、跨项目调度 | 与 `01` §1.1 一致 | 单实例单项目 |
| 飞书卡片交互按钮 | 需要公网回调与卡片 schema 联调 | 文本指令 + 面板；卡片结构在 `04` 已定义，后续接 |

## 3. 架构：六层与依赖方向

```
┌───────────────────────────────────────────────────────────────┐
│ L1 接入  sources/{local,feishu}      协议转换 · 去重 · 游标      │
├───────────────────────────────────────────────────────────────┤
│ L2 领域  domain/{engine,policy,router,gate,stages}             │
│          唯一写入者 · 状态机 · 授权 · 路由 · 门禁规则            │
├───────────────────────────────────────────────────────────────┤
│ L3 执行  executor/{executor,generator,templates,asset-router,repo} │
├───────────────────────────────────────────────────────────────┤
│ L4 资产  <project>/docs · hardware · firmware · software       │
├───────────────────────────────────────────────────────────────┤
│ L5 观测  panel/server                                          │
├───────────────────────────────────────────────────────────────┤
│ L0 基础设施  store/db · util/{yaml,csv,fsx,ids}                │
└───────────────────────────────────────────────────────────────┘
```

**依赖规则（可机械检查）**：

- `domain/*` 只允许 import `store`、`util`、`domain`。**不得** import `executor`、`sources`、`panel`。
- `sources/*` 只允许 import `domain` 的 `Engine` 接口与 `util`。不得 import `executor`。
- `executor/*` 只允许 import `domain`（读规则）、`util`，以及 `child_process`。不得 import `sources`。
- `panel/*` 只读 `store`，不写业务表（唯一例外：签署，走 Engine 方法）。

这与 `01` §4.1 的"领域层不做 I/O"存在一处**有意的偏离**：MVP 的执行器与领域层同进程。代价是依赖规则靠约定与测试守住，而非进程边界。`07` 的演进路径里，把 `executor` 拆成独立进程即可恢复硬边界——接口已按可拆设计（只传 ID 与纯数据）。

## 5. 数据模型

单库 `<project>/.state/orchestrator.sqlite`。设计原则：**状态表只存当前态，过程写 `report` 与 `audit`；不可变对象（Trigger、Mandate、Doc 版本）只插入不更新。**

```sql
-- 事件与聚合
trigger(id PK, source, external_id UNIQUE, thread_id, actor_id, actor_name,
        chat_id, body, at, disposition, meta)          -- disposition: new|duplicate|filtered
thread(id PK, title, stage, source, created_at, updated_at)
eval(id PK, thread_id, trigger_ids, status, verdict, reason,
     task_type, stage, gate_target, severity, assessment, policy_version,
     created_at, decided_at)                            -- status: open|accepted|rejected|unavailable
ticket(id PK, thread_id, eval_id, title, task_type, stage, gate_target, severity,
       status, blocked_reason, created_at, updated_at)  -- status: open|working|review|closed|blocked|dropped
mandate(id PK, ticket_id, repo_scope, stage_scope, action_scope,
        strength, policy_version, granted_by, created_at)
assignment(id PK, ticket_id, attempt, status, workdir, started_at, ended_at, note)
report(id PK, ticket_id, assignment_id, kind, body, at)  -- kind: progress|waiting|ready|blocked|failed
```

```sql
-- 资产与门禁
asset(id PK, ticket_id, kind, doc_type, stage, path, revision, sha256, status, created_at)
gate(id PK, name, stage, status, checks, updated_at, signed_by, signed_at)
       -- status: not_started|preparing|pending|released|returned
outbox(id PK AUTOINCREMENT, kind, dedupe_key UNIQUE, payload, status,
       attempts, next_at, error, created_at)
kv(key PK, value, updated_at)      -- 游标、计数器
audit(id PK AUTOINCREMENT, at, actor, action, subject, detail)
usage(id PK AUTOINCREMENT, at, ticket_id, position, pool, key_id, model, tokens, purpose)
       -- 模型用量：按工单/岗位/池/密钥记账，支撑按工单熔断与成本归因
```

**四个必须由数据库层守住的不变量**

| 不变量 | 实现手段 |
| --- | --- |
| 同一外部事件不产生两个 Trigger | `external_id` 唯一索引 + 插入冲突返回 `duplicate` |
| 一个 Trigger 只被评估一次 | `eval.trigger_ids` 记录，选取待评估时排除已出现的 trigger |
| Mandate 不可变 | 只 `INSERT`，不提供 `UPDATE`；改范围即新工单 |
| 门禁不到 `released` 不能开工下一阶段 | `gate.status` 唯一来源是 `Engine.signGate()` |

## 6. 接口契约

### 6.1 Source（可插拔）

```js
// sources/*.mjs 默认导出
export default {
  kind: 'local' | 'feishu',
  async start(ctx) {},        // 建连/起服务；失败必须抛，不得静默
  async poll() {},            // 返回 Event[]，可为空数组
  async send(reply) {},       // {threadId, text, dedupeKey} → {ok, ref?}
  async stop() {},
}
```

`Event` 形状（**接入层只做协议转换，不做业务判断**）：

```js
{ externalId, threadKey, actorId, actorName, chatId, body, at, addressed, meta }
```

`addressed` 由适配器给出（飞书看 mention；本地模式由测试夹具指定）。**是否准入由 `policy.gate()` 判定，适配器无权决定。**

### 6.2 Executor

```js
runAssignment({ ticket, assignment, project, stateDir }) → {
  status: 'ready' | 'blocked' | 'failed',
  assets: [{ kind, docType, path, revision }],
  commit: { branch, sha } | null,
  prDraftPath: string | null,
  notes: string[]
}
```

执行器**不得**：改 `.superagent/*`、改其他工单的分支、推受保护分支、执行 `blockedCommands` 中的命令。

### 6.3 ModelGateway

```js
generate({ purpose, prompt, schema, budget }) → { text?, object?, usage }
```

配置解析在 `resolveModelConfig()`：**构造参数 > 环境变量 `SUPERAGENT_MODEL_*` > `~/.superagent/model.yml`**，字段级合并。没有 key 时返回 `nullGateway`——文档正文一律来自模板，`generate` 只用于把自然语言标题规范化。**这是刻意的诚实**：没有真模型时不伪造内容。

密钥放 `~/.superagent/model.yml` 而不是项目目录，是因为项目目录会进 Git，靠 `.gitignore` 兜底迟早有人 `git add -f`。自检用 `model --check`，它把连接失败、401/403、404 路径错、429 限流分别给出可操作的提示。

**岗位 → 池的路由**（`executor/positions.mjs` + `executor/keypool.mjs`）：

| 层 | 决定 | 变更频率 |
| --- | --- | --- |
| Policy | 谁能发起、谁能签署 | 组织变动时 |
| 岗位（PM/SE/HW/PE/QE） | 谁负责哪类交付物、用哪套提示词 | 流程调整时 |
| 池（router/worker/doc/vision） | 用哪个模型、哪把 key | 换模型或扩容时 |

三者分离的理由：岗位是**组织概念**，池是**容量概念**。把岗位直接绑到 key 上，一张跨岗位工单会把用量散落到 3–4 把 key，既算不清单工单成本，也无法在限流时腾挪配额。池内多 key 采用"最久未失败优先"，失败即换下一把。

每次调用写 `usage` 表（工单 / 岗位 / 池 / key / 模型 / tokens），因此 `tokensForTicket()` 能直接支撑按工单熔断，`usageSummary()` 能回答"钱花在哪个岗位"。**没有这张表，预算只能靠估算。**

### 6.4 管理 API

`127.0.0.1:<port>`，写操作需 `x-superagent-request: 1`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 面板一次性拉取（概览 + 待办 + 健康） |
| GET | `/api/tickets` `/api/tickets/:id` | 工单列表与全链路（trigger→eval→ticket→asset→report） |
| GET | `/api/gates` | 门禁与检查明细 |
| POST | `/api/gate/:id/sign` | `{by, openId, note}`；校验签署权 |
| POST | `/api/ticket/:id/stop` | 人撤回；执行器不能自我停止 |
| GET | `/api/health` | 各部件健康 + 游标水位 |

错误语义沿用原项目：`400` 参数非法、`403` 越权/缺头、`404` 不存在、`409` 状态冲突。

### 6.5 CLI

| 命令 | 用途 | 退出码 |
| --- | --- | --- |
| `init --code PCU24 --name ...` | 建骨架、套模板、初始化 Git 基线 | 0/1 |
| `run` | 起服务（源轮询 + 执行 + 面板） | 0 正常 / 1 需重启 / 2 部件错 / 3 待配置 |
| `status` | 一次健康检查（供 cron 用） | 同上 |
| `say "..."` | 注入一条消息（本地源），等价于人 @ 机器人 | 0/2 |
| `tickets` / `gate list` / `gate sign` | 查看与签署 | 0/1 |
| `verify` | 全量校验：配置、文档、门禁、追溯 | 0/2 |

## 7. 主链路时序

```
轮询周期（默认 1s，可配）
  │
  ├─1 Source.poll() → Event[]
  │     └▶ Engine.receive(evt)
  │           ├ 幂等：external_id 命中 → duplicate（丢弃，不记 Trigger）
  │           ├ 过滤：actor 是机器人自身 → ignored
  │           └ 落库：Trigger(new) + Thread(无则建)
  │
  ├─2 Engine.pendingThreads() → 每个 thread 取未评估 Trigger
  │     └▶ Engine.evaluate(thread)
  │           ├ Policy.gate()  → 拒绝：eval(rejected) + 按准入表决定是否回一句
  │           └ 通过：Router.assess() → eval(open, assessment)
  │
  ├─3 acceptMode=auto 且 eval 通过 → Engine.accept(eval)
  │     └ 事务内：Ticket(open) + Mandate(不可变) + Assignment(queued) + outbox(致谢)
  │
  ├─4 执行器串行取 Assignment
  │     ├ 建 <stateDir>/work/<ticket>/ 工作目录
  │     ├ 生成文档 → 结构校验 → 资产分类落位
  │     ├ Git：切 agent/<ticket> → 提交 → 写 PR 草案
  │     └ 回报 ready/blocked/failed → Ticket 进 review/blocked/dropped
  │
  ├─5 Engine.refreshGates()：对受影响门禁跑自动检查
  │     └ 通过 → gate(pending)；不通过 → gate(preparing) + 缺口清单
  │
  └─6 outbox 投递：致谢、完成通知、缺口清单（指数退避，5s→300s）
```

**为什么评估与执行分离**：评估必须快（≤2 分钟，`01` §10），执行可能几十分钟。同进程串行实现里，用两个阶段而非两个线程，靠"一次只跑一个 assignment"保证仓库不被并发写。

## 8. 状态机与转换合法性

```
Trigger: new ──▶ consumed
Eval:    open ──▶ accepted | rejected | unavailable
Ticket:  open ──▶ working ──▶ review ──▶ closed
                    │           │
                    ├──▶ blocked ◀┘        （blocked → working 需人给答案或补充信息）
                    └──▶ dropped            （人撤回 / 重复 / 已失效）
Gate:    not_started ──▶ preparing ──▶ pending ──▶ released
                              ▲            │
                              └── returned ┘
```

`Engine.transition()` 用一张显式转换表校验，非法转换抛 `UserError`（固定错误码，不暴露堆栈）。**四条硬规则**：

1. `gate.released` 只能由 `signGate()` 写入，且调用者必须有 `canSign`。
2. `ticket.closed` 前置条件：至少一个 `asset` 且其结构校验通过。
3. `ticket.dropped` 只能由人触发（`/api/ticket/:id/stop` 或 CLI），执行器回报 `failed` 只是 `blocked`。
4. `eval` 一旦 `accepted` 不可重开；重复触发走新 Eval（同 Thread 允许并发 Trigger 合批）。

## 9. 非功能设计

| 关注点 | MVP 做法 | 演进 |
| --- | --- | --- |
| 幂等 | 三层键：事件 `external_id`、文档 `docId`、消息 `dedupeKey` | 保持 |
| 先存储后执行 | outbox 与 assignment 都先落库再动作 | 保持 |
| 崩溃恢复 | 启动时把 `working` 的 assignment 重置为 `queued` 并带恢复备注；outbox `sending` 重置为 `pending` | 加 worktree 保留 |
| 数据完整性 | 单库 WAL；所有多表写在一个 `tx()` | 分库 + 只读副本 |
| 隔离 | 执行器只写 `docs/ hardware/ firmware/ software/` 与 `.state/work/`；`.superagent/` 只读 | 独立进程 + 容器 |
| 安全 | 面板只绑 `127.0.0.1`；写接口校验自定义头；提交前正则扫凭据；禁推受保护分支 | 网关 + 审计链 |
| 可观测 | `audit` 全量事件；`report` 过程留痕；`/api/health` 给退出码 | Prometheus |
| 预算 | `budget.perTicketLimit` 仅记账不阻断（无真实调用） | 网关熔断 |
| 留存 | 文档与 audit 不删除；`recordRetentionYears` 写入 manifest | 归档策略 |

## 10. 关键取舍（相对 `01` 的落地偏差）

| 设计目标 | MVP 实现 | 偏差与影响 |
| --- | --- | --- |
| 领域层不做 I/O | 同进程，但 I/O 全部收敛在 `store`/`executor` | 靠依赖规则 + 测试守边界；可拆 |
| 执行器独立会话 | 进程内函数调用 | 无沙箱隔离；命令白名单为软约束 |
| 模型研判 | 关键词路由 | 复杂/含糊需求会落到"需人工澄清"，这是**设计内行为**而非缺陷 |
| 三通道回写 | 飞书 + 本地文件；PR 草案落盘 | 够验证链路；PR 创建留 `gh` 开关 |
| 阶段门 5 个 | 定义全 5 个，自动检查实现 G1/G2/G3/G4 | G5 无固定终点，只做持续监控 |
| 分支模型 | **堆叠分支**：本工单分支基于上一张工单的分支 | 工作区文档持续累积，门禁能读到全部历史产物；代价是 PR 需按顺序评审。生产应改为 worktree 从 develop 拉出 + 合并后校验 |
| 追溯存储 | 边表 `trace-edges.csv` 与宽表 `traceability.csv` 并存 | 边表供机器反查影响面（本工单产出了什么、影响了什么），宽表供审核时一眼看全链路；两者职责不同，不合并 |

## 11. MVP 验收标准

一条命令能跑完，且每条断言可自动检查：

```bash
node mvp/src/cli.mjs init  --dir demo/PCU24 --code PCU24 --name "电机控制器 2024"
node mvp/src/cli.mjs run   --dir demo/PCU24 --once        # 单轮跑完即退，便于 CI
node mvp/src/cli.mjs say   --dir demo/PCU24 --as ou_zhang "客户投诉 PCU24 低温启动偶发失效，请开 8D"
node mvp/src/cli.mjs verify --dir demo/PCU24
```

| # | 验收项 | 判据 |
| --- | --- | --- |
| A1 | 幂等 | 同一消息投两次，`trigger` 表只增 1 行，`ticket` 只 1 张 |
| A2 | 准入 | 非白名单发送 → eval `rejected`，无 ticket；策略 `acceptMode: off` → 全拒 |
| A3 | 路由 | "投诉/失效" → `quality-8d` / S5；"立项" → `project-init` / S1；含糊文本 → `clarify` |
| A4 | 模板契约 | 生成文档 front-matter 11 个必填键齐全，id 与路径自洽，缺一即结构校验失败 |
| A5 | 分类落位 | 8D 落 `docs/S5-量产/8D/`；ECN 落 `docs/S5-量产/ECN/`；未知类型落 `_unclassified/` |
| A6 | 仓库 | 分支为 `fix/<ticket>` 或 `agent/<ticket>`，不触碰 `main`/`develop`，提交作者为配置身份 |
| A7 | 门禁 | 四份 S1 交付物齐套 → G1 自动检查通过转 `pending`；未签署时 `released` 不可达 |
| A8 | 签署权 | 无 `canSign` 的人签署 → 403，`gate` 状态不变 |
| A9 | 一致性 | PFMEA 出现流程图没有的工序 → G3 检查失败并列出差异 |
| A10 | 可追溯 | 任一 ticket 可反查 trigger → eval → asset → commit |
| A11 | 恢复 | 进程在 `working` 状态被杀，重启后该 assignment 重新入队且不重复提交 |
| A12 | 面板 | `/api/state` 返回待办 ≥1 且含 ticketId；`/api/health` 正常 |

**A1–A12 全部由 `mvp/test/` 覆盖**，`node --test mvp/test` 应全绿。这条规则本身就是设计的一部分：验收标准必须可执行，否则无法判断 MVP 是否完成。

## 13. 演进路径

| 阶段 | 增量 | 触发条件 |
| --- | --- | --- |
| M0（本文） | 闭环可跑、门禁可查、面板可看 | — |
| M1 | 接真实模型网关：研判用模型、文档生成只填"可从上下文确定"的字段 | 网关就绪 + `observe` 两周数据 |
