# 05 仓库与执行器规范

## 1. 仓库拓扑

### 1.1 单仓多目录（推荐）

一个产品线一个仓库，文档、代码、硬件资料同居一仓。

**优点**：追溯简单、一次 PR 可同时改文档与代码、权限统一。
**缺点**：仓库体积增长快（尤其硬件二进制），需要 Git LFS。

### 1.2 多仓分离（备选）

```
product-docs.git        # 文档
product-firmware.git    # 固件
product-hardware.git    # 硬件
```

**适用**：硬件团队与软件团队权限差异大、发布节奏不同。
**代价**：跨仓追溯需要额外索引。

### 1.3 选择建议

| 团队规模 | 建议 |
| --- | --- |
| ≤ 30 人 | 单仓 |
| 30–80 人 | 单仓 + LFS，或代码/硬件分仓 |
| > 80 人 | 多仓 + 中央追溯服务 |

> 本节描述的是稳定态。**新项目从零接入时仓库怎么建、骨架怎么生成、基线怎么冻结**，见 [09-新项目接入](09-新项目接入.md)——那里还给出了三种形态的判定标准与 `scripts/new-project.sh` 生成器。

## 2. 工单工作区

每个工单获得一个独立目录，互不干扰。沿用原项目的 `worktree` 方案。

### 2.1 目录布局

```
<stateDir>/work/<ticket-short-name>/
├── repo/                  # git worktree
├── inputs/                # 飞书附件、截图、日志
├── outputs/               # 中间产物
├── evidence/              # 校验证据（测试日志、截图）
└── .ticket.json           # 工单元数据
```

### 2.2 准备命令

```sh
git -C /srv/src/pcu24 fetch --no-tags \
  "https://github.com/acme/pcu24.git" "HEAD:refs/agent/$TICKET" &&
git -C /srv/src/pcu24 worktree add \
  -b "agent/$TICKET" "$WORKDIR/repo" "refs/agent/$TICKET"
```

**要求**：

- 准备命令有 10 分钟超时；
- 失败则工单置 `blocked` 并回报原因；
- 重试复用同一 worktree，不重复 clone；
- 工单结束后保留 7 天再清理（便于追溯）。

### 2.3 隔离边界

| 资源 | 隔离方式 |
| --- | --- |
| 工作目录 | 每工单独立 worktree |
| Git 凭据 | 专用 agent 账号 + 独立配置目录 |
| 环境变量 | 剔除含 KEY/PASSWORD/SECRET/TOKEN 的变量 |
| 网络 | 默认允许，敏感项目可配置白名单 |
| 进程 | 每工单一个会话，互不可见 |

## 3. 分支与提交

### 3.1 执行器允许的操作

| 操作 | 允许 | 说明 |
| --- | --- | --- |
| 创建 `agent/<ticket>` | 是 | 自动 |
| 在 `agent/*`、`feature/*`、`change/*`、`fix/*` 提交 | 是 | 仅限授权范围内文件 |
| 推送上述分支 | 是 | 仅限 agent 账号 |
| 创建 PR | 是 | 目标 `develop` |
| 合并 PR | 否 | 必须由人 |
| 推送 `main` / `develop` / `release/*` | 否 | 硬禁止 |
| 打标签 | 仅 `releaser` 预设 | 发布工单 |
| 强制推送 | 否 | 硬禁止 |
| 删除他人分支 | 否 | 硬禁止 |

### 3.2 提交前钩子

```
pre-commit:
  1. 检查是否在禁止分支
  2. 检查改动文件是否在 Mandate 范围内
  3. 文档：front-matter 校验
  4. 硬件：manifest 与 sha256 校验
  5. 代码：lint + 单元测试（快速集）
  6. 提交信息格式校验（含 Refs: TKT-xxx）

pre-push:
  1. 再次检查分支
  2. 检查是否包含大文件（> 10MB 且未走 LFS）
  3. 检查是否含密钥（正则扫描）
```

任一失败则阻止提交，并把原因写入工单报告。

### 3.3 PR 描述模板

```markdown
## 工单
TKT-2026-0031

## 变更类型
设计变更 / 文档 / 硬件

## 变更内容
- 过温降额策略由固定阈值改为线性降额
- 更新 DFMEA 条目 DFMEA-012
- 更新控制计划 CP-020

## 影响分析
- 影响特殊特性：CC-03（过温保护）
- 需重新验证：DVP-THERM-04
- 硬件无变更

## 验证证据
- 单元测试：通过（见 evidence/unit.log）
- HIL 测试：通过（见 evidence/hil.log）

## 追溯
- 需求：REQ-001
- ECN：ECN-2026-007
```

## 4. 执行器预设

按阶段拆分工具集，遵循最小权限。

### 4.1 预设定义

| 预设 | 阶段 | 文件写 | Shell | 测试 | 打标签 | 合并 PR |
| --- | --- | --- | --- | --- | --- | --- |
| `planner` | S1 | 仅 `docs/` | 只读 | 否 | 否 | 否 |
| `designer` | S2 | `docs/`、`hardware/` | 只读 | 否 | 否 | 否 |
| `process` | S3 | `docs/` | 只读 | 否 | 否 | 否 |
| `verifier` | S4 | `docs/`、`evidence/` | 执行测试 | 是 | 否 | 否 |
| `releaser` | S5 | `docs/`、`hardware/_released/` | 构建 | 是 | 是 | 否 |
| `fixer` | 任意 | 授权目录 | 执行 | 是 | 否 | 否 |

### 4.2 工具集

每个预设包含：

- 文件读写（限定目录）
- Shell（前台命令 5 秒转后台，避免阻塞消息）
- 模板渲染
- 校验器（front-matter、manifest、追溯）
- Git 操作（受限）
- 技能加载

不包含：

- 向人提问（走结构化 `human_action`）
- 修改 profile
- 跨工单访问
- 网络浏览（除测试需要）

## 5. Skills 设计

技能是"按需加载的领域知识"，避免把所有规则塞进系统提示词。

### 5.1 技能清单

| 技能 | 触发场景 | 内容 |
| --- | --- | --- |
| `iatf16949` | 任何阶段任务 | 五阶段定义、门禁检查项、交付物清单 |
| `dfmea` | 写/改 DFMEA | 七步法、S/O/D 评分准则、措施优先级 |
| `pfmea` | 写/改 PFMEA | 过程步骤、失效模式库、控制措施 |
| `control-plan` | 写/改控制计划 | 特性、规格、频次、反应计划 |
| `msa` | 做测量系统分析 | GRR 方法、判定准则、样本量 |
| `spc` | 做过程能力 | Cpk/Ppk 计算、控制图选择 |
| `ppap` | 准备 PPAP | 18 项要素、提交等级 |
| `8d` | 处理质量问题 | D1–D8、5Why、鱼骨图 |
| `ecn` | 变更管理 | 影响分析、分级、审批流 |
| `repo-ops` | 任何仓库操作 | 分支、提交、PR 规范 |
| `feishu-reply` | 回写消息 | 消息格式、长度、静默规则 |
| `bom` | 硬件 BOM | 列定义、车规等级、替代料规则 |

### 5.2 技能结构

```
skills/<name>/
├── SKILL.md          # 触发条件、步骤、输出要求
├── references/       # 标准条款、评分表
└── templates/        # 该技能使用的模板
```

## 6. 文档生成流水线

```
选择模板 → 填充已知字段 → 标记待人工补充 → 校验 → 生成草稿 → 提交 PR → 通知责任人
```

### 6.1 填充策略

| 字段来源 | 示例 |
| --- | --- |
| 工单元数据 | 项目、阶段、责任人、日期 |
| 追溯矩阵 | 关联需求、上下游文档 |
| 飞书消息 | 问题描述、期望 |
| 历史文档 | 同类项目的默认值 |
| 模型生成 | 分析性内容（需人工复核） |

### 6.2 待补充标记

模型不确定的内容用显式标记，不允许编造：

```markdown
> ⚠ 待补充：该特性的 S/O/D 评分需由设计工程师确认。
> 建议值：S=7, O=4, D=5（基于同类项目 DFMEA-008）
```

校验器会统计待补充项数量，超过阈值则不允许进入 `review` 状态。

## 7. 硬件资源操作

### 7.1 允许的自动操作

- 更新 BOM 的 CSV 版本与 manifest；
- 生成 BOM 差异报告；
- 校验位号与原理图一致性；
- 归档新版本到 `_released/`；
- 更新 `compatibility.yml`。

### 7.2 禁止的自动操作

- 修改原理图源文件（二进制，需专业工具）；
- 生成或修改 Gerber；
- 修改结构 3D 模型；
- 批准硬件版本发布。

### 7.3 二进制文件处理

- 统一走 Git LFS；
- 每次提交重算 `sha256` 并写入 manifest；
- 大文件（> 50MB）需人工确认是否入库；
- 历史版本保留在 `_released/`，不依赖 Git 历史回溯。

## 8. 并发与资源控制

| 资源 | 限制 | 说明 |
| --- | --- | --- |
| 并发执行器 | 默认 4 个 | 按机器配置调整 |
| 人工消息 | 额外 1 个槽位 | 保证人不被机器阻塞 |
| 单工单后台任务 | 30 分钟上限 | 超时终止并报告 |
| 测试任务 | 按队列 | 避免同时占用测试台 |
| 仓库推送 | 串行 | 避免分支冲突 |

## 9. 失败与恢复

| 场景 | 处理 |
| --- | --- |
| 准备命令失败 | 工单 `blocked`，回报具体错误，可重试 |
| 提交被钩子拒绝 | 修正后重试，最多 3 次，仍失败则转人工 |
| 推送冲突 | 拉取最新后 rebase，冲突则转人工 |
| PR 创建失败 | 重试 3 次，保留分支与提交 |
| 测试超时 | 终止并记录，工单 `blocked` |
| 进程重启 | 新执行器先核对目录、Git 历史、PR 状态，再继续 |
| 仓库不可用 | 本地提交暂存，登记待推送队列 |

## 10. 提交信息与审计

每次提交自动附加：

```
Refs: TKT-2026-0031
Agent: electronics-superagent
Mandate: MND-0031
```

审计日志记录：

- 谁触发的工单；
- 授权范围；
- 执行器做了什么；
- 改了哪些文件；
- 何时推送、何时创建 PR；
- 谁合并的。

## 11. 检查清单

执行器在开 PR 前自检：

- [ ] 分支为 `agent/*` 或授权分支
- [ ] 改动文件均在 Mandate 范围内
- [ ] 文档 front-matter 完整
- [ ] 硬件 manifest 已更新
- [ ] 追溯矩阵已更新
- [ ] 提交信息合规
- [ ] PR 描述模板完整
- [ ] 证据文件已附
- [ ] 未触碰禁止分支
