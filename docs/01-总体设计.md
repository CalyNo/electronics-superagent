# 01 总体设计

## 1. 设计目标

构建一个**单信息源、阶段化、可授权、可追溯**的工程智能体，使汽车电子研发团队能够：

1. 用一句话在飞书里发起需求、变更或质量问题；
2. 由系统自动判定阶段、任务类型与所需交付物；
3. 按 IATF 16949 / APQP 流程产出规范文档、代码与硬件资料；
4. 自动完成仓库操作（分支、提交、PR、标签、追溯矩阵）；
5. 在需要人决策的节点准确地把问题抛回给人，而不是替人决策。

### 1.1 非目标

- **不做**多信息源聚合（Jira、钉钉、邮件、PLM 暂不接入）。
- **不做**阶段门自动放行。系统只准备证据、做一致性校验，放行签字必须由人完成。
- **不做**替代 PLM/ERP。系统产出文件并同步到仓库，不承担 BOM 主数据管理职责。
- **不做**跨项目调度。一个实例服务一个产品线（对应原项目"一个仓库"的约束）。
- **不做**模型自主扩大授权。授权范围只能由人通过策略变更来扩大。

## 2. 设计哲学

继承 `dsh-superagent` 的三条原则，并针对制造业补充两条。

| 原则 | 来源 | 在本方案中的含义 |
| --- | --- | --- |
| 注意力最小化 | 原项目 | 一条消息只解决一个决策；无进展不发言；健康状态不占版面 |
| 先授权后执行 | 原项目 | 每张工单必须绑定 Mandate；上下文（如聊天记录）不授予权限 |
| 事实优先于文本 | 原项目 | 权限、阶段门、分类规则由代码与配置强制；聊天内容永远只是数据 |
| 模板即契约 | 本方案新增 | 文档必须套模板；字段缺失即校验失败，不允许"自由发挥" |
| 证据可追溯 | 本方案新增 | 需求 → 工单 → 文档 → 提交 → 版本，链路完整可反查 |

## 3. 领域模型映射

原项目的领域模型是精心裁剪过的，本方案不新增核心概念，只做**语义替换**与**属性扩展**。这是控制复杂度的关键。

| 原概念 | 本方案概念 | 定义 | 关键规则 |
| --- | --- | --- | --- |
| Source | 飞书来源 | 唯一的消息事件流 | 保存读取游标；丢弃机器人自身消息；翻译为 Thread |
| Trigger | 触发事件 | 一条不可变的飞书消息/卡片提交 | 带发送者、群、项目标签；幂等键防重复接单 |
| Thread | 需求线程 | 同一需求/问题下的消息时序集合 | 同一线程同时只有一个 Eval；可挂多张工单 |
| Correlation | 关联 | 跨线程的引用关系（如变更单引用原需求） | 只补充上下文，不路由 |
| Channel | 回写通道 | 飞书话题、仓库 PR、文档库 | 一个线程可有多个通道 |
| Policy | 工程策略 | 角色矩阵、项目准入、阶段权限、规则集 | 版本化；变更影响运行中工单但不撤销授权 |
| Eval | 评估 | 准入（Gate）+ 研判（Assessment） | 两层；输出接单/停止/忽略/不可用 |
| Mandate | 授权 | 允许的项目、仓库、阶段门、动作集合 | 不可变；扩大范围须新工单；只由人撤回 |
| Ticket | 工单 | 一个受权的工程任务 | 自有状态机；不跟随执行器状态 |
| Assignment | 派工 | 工单与一次执行器实例的绑定 | 一个工单可多次派工（重试、恢复） |
| Subscription | 订阅 | 工单与线程的多对多关系 | 扇出消息作为上下文，不授予权限 |
| Executor | 执行器 | 独立会话 + 独立目录 | 每工单一个；工具集按阶段裁剪 |
| Attention | 待人工决策 | 工单上等待人回答的问题 | 结构化字段，不靠自由文本推断 |
| Report | 报告 | 执行器回报的状态 | progress / waiting / ready / blocked / failed / dropped |

### 3.1 新增的行业属性（不新增概念）

| 承载概念 | 新增属性 | 说明 |
| --- | --- | --- |
| Trigger | `projectId`、`requesterRole` | 项目标识与请求者角色，用于准入 |
| Thread | `stage`、`docSetId` | 当前 APQP 阶段、关联文档集 |
| Ticket | `taskType`、`severity`、`gateTarget` | 任务类型（开发/变更/质量/文档）、严重度、目标阶段门 |
| Mandate | `repoScope`、`stageScope`、`actionScope` | 仓库范围、阶段范围、允许动作 |
| Executor | `preset`、`skills` | 阶段化预设与技能包 |

## 4. 架构分层

```
┌─────────────────────────────────────────────────────────────┐
│  接入层  Feishu Adapter（事件订阅 / 卡片回调 / 消息发送）      │
├─────────────────────────────────────────────────────────────┤
│  领域层  Engine（唯一写入者）                                 │
│    Intake → Evals → Tickets → Assignments → Replies          │
│    Policy（版本化）  Templates（模板注册与校验）               │
├─────────────────────────────────────────────────────────────┤
│  执行层  Executor（会话 + 目录 + 工具集 + Skills）             │
│    Stage Runner：APQP 阶段任务编排                            │
│    Asset Router：文档 / 代码 / 硬件资源分流                   │
├─────────────────────────────────────────────────────────────┤
│  资产层  Git 仓库（docs / hardware / firmware / software）    │
│    Traceability Matrix（追溯矩阵）                            │
├─────────────────────────────────────────────────────────────┤
│  观测层  Panel（驾驶舱 / 阶段门看板 / 审计日志）               │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 分层职责与依赖规则

| 层 | 职责 | 禁止 |
| --- | --- | --- |
| 接入层 | 协议转换、签名校验、事件去重 | 不含业务规则；不直接读写仓库 |
| 领域层 | 状态机、授权、策略、模板校验 | 不做 I/O；不调用外部 API |
| 执行层 | 实际干活：写文档、改代码、跑测试 | 不绕过领域层直接改工单状态 |
| 资产层 | 持久化与版本化 | 不含流程逻辑 |
| 观测层 | 只读展示与审计 | 不写业务数据 |

**依赖方向**：接入层 → 领域层 ← 执行层；领域层不依赖任何外层。这与原项目"core 不做 I/O"的约束一致。

## 5. 核心工作流

### 5.1 七步主链路

| 步骤 | 动作 | 产出 | 失败处理 |
| --- | --- | --- | --- |
| 1 | 飞书消息进入，翻译为 Trigger | 标准化事件 | 格式非法则记录并丢弃 |
| 2 | 幂等检查 | 新事件 / 重复 | 重复直接忽略 |
| 3 | Gate 准入 | 明权 / 推断 / 拒绝 | 拒绝则静默或提示一次 |
| 4 | Assessment 研判 | 阶段、类型、风险、交付物清单 | 超时重试两次，第三次记不可用 |
| 5 | 创建工单与授权 | Ticket + Mandate + Assignment | 事务内完成，失败回滚 |
| 6 | 执行器干活 | 文档、代码、硬件资料、PR | 失败则报告并等待人处理 |
| 7 | 回写与阶段门 | 飞书答复 + PR 链接 + 门禁状态 | 通道失效则降级到备用通道 |

### 5.2 状态机

**工单状态**（自有，不跟随执行器）：

```
待准入 → 已接单 → 执行中 → 待评审 → 已关闭
                    ↑         ↓
                    └─ 阻塞/失败（等人）
```

**阶段门状态**（独立于工单）：

```
未开始 → 准备中 → 待签署 → 已放行 / 已退回
```

关键规则：**阶段门状态不能由执行器直接改写**。执行器只能提交"门禁证据包"，由人签署后由系统记录放行。

## 6. 阶段化执行模型

这是本方案与原项目最大的差异：原项目的执行器只有一种工作模式，本方案按 APQP 阶段拆分执行职责。

| 阶段 | 执行器预设 | 主要工具 | 产出 |
| --- | --- | --- | --- |
| S1 策划 | `planner` | 文档生成、模板校验、甘特图 | 项目计划、可行性分析、团队矩阵 |
| S2 产品设计 | `designer` | 文档、原理图检查、DFMEA、DVP | 需求规格、DFMEA、DVP、特殊特性 |
| S3 过程设计 | `process` | 过程流程图、PFMEA、控制计划 | 过程流程图、PFMEA、控制计划 |
| S4 验证 | `verifier` | 测试执行、MSA、SPC、报告生成 | MSA 报告、过程能力、试产报告 |
| S5 量产准备 | `releaser` | PPAP 清单、版本标签、发布 | PPAP 包、量产基线、追溯矩阵 |

每个预设的工具集遵循最小权限：

- `planner` / `designer` / `process`：可写文档，**不可**打标签、不可合并 PR。
- `verifier`：可跑测试与采集数据，**不可**改设计文档。
- `releaser`：可打标签、生成发布包，**不可**修改设计内容。

## 7. 三类资产的分类与路由

执行器在产出任何文件前，必须先经过**资产路由器**判定归属：

```
产物 → 类型判定 → 分类编码 → 目标路径 → 模板校验 → 落盘 → 登记追溯矩阵
```

| 资产类型 | 判定依据 | 默认根目录 | 版本策略 |
| --- | --- | --- | --- |
| 文档 | 模板 ID、扩展名 `.md`/`.docx`/`.pdf` | `docs/<阶段>/<类型>/` | 语义版本 + 审批记录 |
| 代码 | 语言、模块归属、固件/上位机 | `firmware/`、`software/` | Git 分支 + 标签 |
| 硬件资源 | BOM、原理图、PCB、结构、工装 | `hardware/<类别>/` | 硬件版本号 + 变更单 |

详细规则见 [03-资产分类规范](03-资产分类规范.md)。

## 8. 授权模型

### 8.1 三层授权

| 层 | 决定什么 | 示例 |
| --- | --- | --- |
| 身份层（Gate） | 谁可以发起 | 只有"硬件工程师"角色可在"研发群"提设计变更 |
| 范围层（Mandate） | 可以做什么 | 允许改 `hardware/bom/` 与 `docs/S2-设计/`，不允许动 `firmware/` |
| 阶段层（Gate Check） | 现在能不能做 | S2 未放行，不允许启动 S4 的 PPAP 工作 |

### 8.2 授权强度

| 强度 | 触发条件 | 能力 |
| --- | --- | --- |
| explicit | 白名单成员直接 @ 智能体 | 可创建工单、可指定阶段 |
| inferred | 白名单成员在已订阅线程中补充信息 | 只能补充上下文，不能开新工单 |
| not admitted | 非白名单、机器人、外部群 | 一律拒绝 |

### 8.3 不可变与撤回

- Mandate 一旦创建不可修改；扩大范围必须新开一张工单。
- 只有人能撤回授权（飞书指令或面板操作）。
- 策略变更会向受影响工单投递"策略变更通知"，但不立即撤销授权；工单恢复前会重新校验。

## 9. 可靠性与恢复

沿用原项目的工程约束，并针对制造业补充：

| 机制 | 做法 |
| --- | --- |
| 先存储后执行 | 任何派工、投递、回写先落库，再执行；失败按指数退避重试 |
| 幂等 | Trigger 用 `feishu:<message_id>` 作为唯一键；PR 用分支名去重 |
| 断点恢复 | 重启后执行器先核对目录、Git 历史、PR 状态，再决定是否重复外部动作 |
| 并发控制 | 每线程同时一个 Eval；每工单一个执行槽；人工消息可占用额外槽位 |
| 通道降级 | 飞书不可用时，结果暂存并在恢复后补发；仓库不可用时，文档先落本地并登记待提交 |
| 数据留存 | 所有工单、决策、文档版本按 IATF 记录保存要求留存（默认 15 年，可配置） |

## 10. 观测与度量

面板只回答三个问题（沿用原项目）：

1. **现在有什么需要我？** —— 待决策工单、阶段门待签署、阻塞项。
2. **系统健康吗、在做对的事吗？** —— 各部件健康度、近 24 小时接单/拒绝/失败统计、阶段门通过率。
3. **一件事的完整历史是什么？** —— 从 Trigger 到 Eval 到 Ticket 到文档与提交的全链路。

核心度量：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 一次通过率 | 无需人工返工的工单占比 | ≥ 70% |
| 平均接单时延 | 消息到工单创建 | ≤ 2 分钟 |
| 阶段门准时率 | 按计划通过的门占比 | ≥ 85% |
| 文档返工率 | 因模板/字段问题被退回的比例 | ≤ 10% |
| 注意力占用 | 每条消息平均需要人回复的次数 | ≤ 1.2 |

## 11. 关键设计取舍

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 单信息源 | 只接飞书 | 降低接入复杂度，先跑通闭环 | 无法覆盖邮件/供应商门户 |
| 阶段门人工 | 人签署 | 质量责任不可转移给模型 | 吞吐受限于人 |
| 模板强校验 | 字段缺失即失败 | 保证文档可比、可审计 | 初期填写成本高 |
| 多仓库分层 | 单仓多目录 | 追溯简单、权限统一 | 大团队可能有耦合 |
| 观察模式默认 | `observe` 起步 | 用真实数据校准规则 | 见效慢 2–4 周 |

## 12. 与论文/原项目的差异说明

原项目强调"一个仓库、一种工作模式"。本方案在其上增加了**阶段维度**，原因是制造业的质量体系天然是阶段化的，且阶段门是合规要求。这一扩展不引入新的核心概念，只把阶段作为 Mandate 与 Executor 的属性，保持了领域模型的简洁性。
