# 07 部署与实施路线图

## 1. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 宿主运行时 | DeepSeek Harness（DSH） | 提供 Session、工具、技能、定时任务 |
| 插件框架 | Cordis | 插件装配与热重载 |
| 业务运行时 | Node.js 22+ / TypeScript | 与原项目一致 |
| 持久化 | SQLite | 单文件、事务、易备份 |
| 消息通道 | 飞书开放平台 | 自建应用 + 机器人 |
| 仓库 | Git（GitHub/GitLab/Gitee） | 支持 API 与 LFS |
| 校验 | Zod | 配置与模板字段校验 |
| 观测 | 内置面板 + 结构化日志 | 驾驶舱与审计 |

### 2.2 Profile 隔离

沿用原项目的做法：独立 profile，避免与日常使用冲突。

```
~/.dsh/profiles/electronics/
├── cordis.patch.yml     # 机器配置
└── ...
```

`cordis.patch.yml` 关键项：

```yaml
- insert:
    - id: electronics-superagent
      name: electronics-superagent
      config:
        stateDir: /srv/superagent/state
        feishu:
          appId: cli_xxx
          cli: /home/agent/.local/bin/lark-electronics
        repo:
          url: https://github.com/acme/pcu24.git
          workdir: /srv/src/pcu24
          cli: /home/agent/.local/bin/gh-agent
        webserver:
          port: 3082
```

### 2.3 账号与凭据

| 账号 | 用途 | 隔离 |
| --- | --- | --- |
| 飞书机器人 | 收发消息 | 独立 app，独立配置目录 |
| Git agent 账号 | 提交与 PR | 独立 `GH_CONFIG_DIR` |
| 模型账号 | 推理 | 密钥管理 |

**原则**：所有凭据独立，不共享个人账号。

## 3. 启动与运维

### 3.1 启动

```sh
scripts/electronics-superagent start
scripts/electronics-superagent status
```

### 3.2 健康检查

| 退出码 | 含义 | 处理 |
| --- | --- | --- |
| 0 | 正常 | 静默 |
| 1 | 未运行/重复/无响应 | 重启 |
| 2 | 部件报错 | 查看 `errors`，不重启 |
| 3 | 待配置 | 查看 `setup` |

### 3.3 定时巡检

在日常 profile 中创建每小时任务：

```
运行 status：
- 0：静默
- 2：报告 errors，不重启
- 3：报告 setup 缺失项
- 1：restart，仍失败则读日志并报告
```

| 硬件发布包 | 每次发布 | 永久 |

## 4. MVP 范围

### 4.1 第一版做什么

**目标**：把"质量问题 8D"跑通端到端。

| 能力 | 范围 |
| --- | --- |
| 飞书接入 | 单群、@ 触发、话题回复 |
| 准入 | 人员白名单 + 群绑定 |
| 研判 | 只识别"质量问题"一类 |
| 工单 | 单一类型：8D |
| 模板 | 8D 报告（1 份） |
| 执行器 | 单预设，只写 `docs/S5-量产/8D/` |
| 仓库 | 只提交文档，不改代码 |
| 阶段门 | 无（8D 走时限） |
| 面板 | 工单列表 + 超时提醒 |

**为什么选 8D**：

- 结构固定（D1–D8）；
- 时限明确，痛点集中；
- 不涉及代码与硬件变更，风险低；
- 见效快，容易获得管理层支持。

### 4.2 第一版不做什么

- 多群、多项目；
- 代码自动修改；
- 硬件 BOM 操作；
- 阶段门签署；
- 文档自动分类（先手工，后自动）。

## 5. 迭代路线

| 阶段 | 周期 | 目标 | 关键交付 |
| --- | --- | --- | --- |
| P0 MVP | 4–6 周 | 8D 跑通 | 飞书接入、8D 模板、单预设执行器 |
| P1 扩展 | 6–8 周 | 变更管理 | ECN 模板、影响分析、文档分类 |
| P2 设计 | 8–10 周 | S2/S3 文档 | DFMEA/PFMEA/控制计划模板、阶段门 |
| P3 代码 | 8–10 周 | 仓库自动化 | 分支、提交、PR、校验钩子 |
| P4 硬件 | 6–8 周 | BOM 与资料 | BOM 校验、manifest、版本对应 |
| P5 全流程 | 持续 | 五阶段贯通 | 追溯矩阵、驾驶舱、度量 |

### 5.1 每阶段的验收标准

| 阶段 | 验收 |
| --- | --- |
| P0 | 10 个真实 8D 全流程跑通，一次通过率 ≥ 60% |
| P1 | 5 个真实变更跑通，影响分析无遗漏 |
| P2 | 3 个项目完成 S2/S3 文档，阶段门一次通过 |
| P3 | 代码 PR 自动化率 ≥ 50%，无越权提交 |
| P4 | BOM 校验拦截 ≥ 3 类真实错误 |
| P5 | 全链路追溯可查，审计通过 |

## 8. 风险与应对

| 风险 | 影响 | 概率 | 应对 |
| --- | --- | --- | --- |
| 模板不符合体系 | 文档返工、审核不通过 | 高 | 质量代表前置评审，先小范围试用 |
| 模型生成内容不准确 | 技术错误流入文档 | 高 | 强制"待补充"标记 + 人工复核 |
| 权限配置错误 | 越权或数据泄露 | 中 | 最小权限 + 定期审计 + 演练 |
| 飞书接口变更 | 接入失效 | 中 | 抽象适配层，隔离协议变化 |
| 团队抵触 | 推行受阻 | 中 | 从痛点切入，先做"减负"而非"替代" |
| 仓库体积膨胀 | 克隆变慢 | 中 | Git LFS + 定期归档 |
| 记录保存不完整 | 审计失败 | 低 | 自动归档 + 定期校验 |
| 模型成本超预期 | 预算压力 | 中 | 分级模型 + 缓存 + 限额 |

## 10. 回滚方案

| 场景 | 回滚动作 |
| --- | --- |
| 模型输出严重错误 | 切 `observe` 模式，停止自动执行 |
| 权限配置错误 | 立即停用相关规则，恢复上一策略版本 |
| 飞书接入故障 | 停用 Source，转人工处理 |
| 仓库误操作 | 利用 Git 历史恢复，审计定位 |
| 整体不可用 | 停止服务，团队回到原有流程 |

**原则**：任何自动化都必须有"一键停用"开关，且停用不影响既有数据。
