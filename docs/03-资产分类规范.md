# 03 资产分类规范

## 1. 设计原则

分类不是为了"整齐"，而是为了三件事：

1. **可路由**：执行器拿到产物后，不需要人告诉它放哪里。
2. **可校验**：模板、字段、命名、版本都能被程序检查。
3. **可追溯**：任意一份文件都能反查到需求、工单、授权与变更。

因此本规范采用**三段式分类编码**：`域 / 阶段 / 类型`，再加可选的项目与版本修饰。

```
DOC-S2-DFMEA-001@v1.2
 │   │   │    │   └── 版本
 │   │   │    └────── 流水号
 │   │   └─────────── 类型
 │   └─────────────── 阶段
 └─────────────────── 域（DOC/CODE/HW）
```

## 2. 仓库总体结构

单仓多目录，一个产品线一个仓库。理由：追溯简单、权限统一、跨资产引用方便。

> 该结构由 `scripts/new-project.sh` 生成，新项目从零建仓的流程见 [09-新项目接入](09-新项目接入.md)。

```
<product-repo>/
├── docs/                     # 文档资产
│   ├── _templates/           # 模板（只读，由平台维护）
│   ├── _index/               # 索引与追溯矩阵
│   ├── S1-策划/
│   ├── S2-产品设计/
│   ├── S3-过程设计/
│   ├── S4-验证/
│   ├── S5-量产/
│   └── _archive/             # 作废与历史版本
├── hardware/                 # 硬件资源
│   ├── bom/
│   ├── schematic/
│   ├── pcb/
│   ├── mechanical/
│   ├── fixture/
│   ├── datasheet/
│   └── _released/
├── firmware/                 # 嵌入式固件
├── software/                 # 上位机 / 测试软件
├── test/                     # 测试用例与脚本
├── tools/                    # 构建与校验工具
└── .superagent/              # 智能体配置与状态
    ├── manifest.yml
    ├── rules.yml
    └── taxonomy.yml
```

## 3. 文档分类

### 3.1 分类维度

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 阶段 | S1–S5 | 对应 APQP 阶段 |
| 类型 | 见下表 | 文档性质 |
| 密级 | public / internal / confidential / restricted | 控制访问与是否可外发 |
| 状态 | draft / review / released / obsolete | 生命周期 |
| 项目 | 项目代号 | 多项目共用仓库时区分 |

### 3.2 文档类型编码

| 编码 | 类型 | 模板 | 阶段 |
| --- | --- | --- | --- |
| CHTR | 项目章程 | 01 | S1 |
| SRS | 需求规格书 | 02 | S1 |
| APQP | APQP 项目计划 | 03 | S1 |
| FEAS | 可行性分析 | 04 | S1 |
| DFMEA | 设计 FMEA | 05 | S2 |
| DVP | 设计验证计划 | 06 | S2 |
| SC | 特殊特性清单 | 07 | S2 |
| PFC | 过程流程图 | 08 | S3 |
| PFMEA | 过程 FMEA | 09 | S3 |
| CP | 控制计划 | 10 | S3 |
| MSA | 测量系统分析 | 11 | S4 |
| SPC | 过程能力报告 | 12 | S4 |
| TR | 试产报告 | 13 | S4 |
| PPAP | PPAP 提交清单 | 14 | S4 |
| 8D | 8D 问题报告 | 15 | S5 |
| ECN | 工程变更通知 | 16 | S5 |
| MIN | 会议纪要 | 通用 | 任意 |
| REV | 评审记录 | 通用 | 任意 |
| RISK | 风险登记册 | 通用 | 任意 |

### 3.3 目录与命名

**目录**：`docs/<阶段>/<类型>/`

**文件名**：`<类型编码>-<项目代号>-<流水号>-<简述>.md`

示例：

```
docs/S2-产品设计/DFMEA/DFMEA-PCU24-012-电机控制器功率级.md
docs/S3-过程设计/CP/CP-PCU24-003-SMT贴片工序.md
docs/S5-量产/8D/8D-PCU24-031-客户投诉过温保护失效.md
```

**命名规则**：

- 只用中文、英文、数字、连字符；不用空格、下划线、括号。
- 简述不超过 20 个汉字，能独立表意。
- 流水号三位，全局递增，不复用。
- 文件名一旦发布不得改名；作废时移入 `_archive/` 并保留原名。

### 3.4 文档元数据（front-matter）

所有文档必须以 YAML front-matter 开头，供系统校验与索引：

```yaml
---
id: DOC-S2-DFMEA-012
title: 电机控制器功率级 DFMEA
project: PCU24
stage: S2
type: DFMEA
revision: v1.2
status: review
classification: confidential
owner: 张工
reviewers: [李工, 王工]
created: 2026-11-21
updated: 2026-11-25
related:
  requirements: [REQ-001, REQ-007]
  specialCharacteristics: [CC-03]
  eCN: null
traceability:
  upstream: [DOC-S1-SRS-002]
  downstream: [DOC-S3-PFC-001, DOC-S3-CP-001]
---
```

**必填字段**：`id`、`title`、`project`、`stage`、`type`、`revision`、`status`、`owner`、`created`、`updated`。

**校验规则**（执行器在提交前自动检查）：

1. `id` 与文件路径、文件名一致。
2. `type` 必须在类型编码表中存在。
3. `stage` 必须与所在目录一致。
4. `status` 为 `released` 时，`reviewers` 不得为空。
5. `related.requirements` 不得为空（除通用文档）。
6. `traceability.upstream` 指向的文档必须存在。

## 4. 代码分类

### 4.1 模块划分

| 目录 | 语言/类型 | 职责 | 负责人角色 |
| --- | --- | --- | --- |
| `firmware/app/` | C/C++ | 应用逻辑 | 嵌入式工程师 |
| `firmware/drivers/` | C | 外设驱动 | 嵌入式工程师 |
| `firmware/bsp/` | C | 板级支持包 | 嵌入式工程师 |
| `firmware/bootloader/` | C | 引导程序 | 嵌入式工程师 |
| `firmware/config/` | C/JSON | 编译配置与参数 | 嵌入式工程师 |
| `software/gui/` | 任意 | 上位机界面 | 上位机工程师 |
| `software/tools/` | Python/C# | 测试与产线工具 | 测试工程师 |
| `test/unit/` | 与主语言一致 | 单元测试 | 开发工程师 |
| `test/hil/` | Python | 硬件在环测试 | 测试工程师 |

### 4.2 代码分类编码

用于追溯矩阵与发布包：

```
CODE-<模块>-<功能>-<序号>
CODE-FW-MOTOR-003     # 固件-电机控制-第3个功能块
CODE-SW-CANTOOL-001   # 上位机-CAN工具-第1个功能块
```

### 4.3 分支策略

| 分支 | 用途 | 生命周期 | 保护 |
| --- | --- | --- | --- |
| `main` | 量产基线 | 永久 | 禁止直推，需 PR + 评审 |
| `develop` | 集成基线 | 永久 | 禁止直推 |
| `feature/<ticket>-<简述>` | 新功能 | 工单周期 | 允许执行器推送 |
| `change/<ecn>-<简述>` | 变更实施 | 变更周期 | 允许执行器推送 |
| `fix/<ticket>-<简述>` | 缺陷修复 | 工单周期 | 允许执行器推送 |
| `release/<版本>` | 发布候选 | 发布周期 | 只允许发布执行器 |
| `agent/<ticket>` | 执行器工作分支 | 工单周期 | 由系统创建与清理 |

**规则**：

- 执行器只在 `agent/*`、`feature/*`、`change/*`、`fix/*` 上提交。
- 合并到 `develop` 需 PR + 至少一名代码评审人。
- 合并到 `main` 需 PR + 评审 + 测试通过 + 变更单（如需）。
- 执行器不得直接推送 `main`、`develop`、`release/*`。

### 4.4 提交规范

采用 Conventional Commits，且必须带工单号：

```
<type>(<scope>): <subject>

<body>

Refs: <ticket-id>
```

| type | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档 |
| refactor | 重构 |
| test | 测试 |
| chore | 构建/工具 |
| hw | 硬件资料变更 |

示例：

```
feat(firmware/motor): 增加过温降额策略

在结温超过 125°C 时线性降低输出功率，150°C 时关断。

Refs: TKT-2026-0031
```

### 4.5 版本与标签

| 对象 | 版本格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 固件 | `fw-<主>.<次>.<修订>` | `fw-1.4.2` | 主版本不兼容、次版本新增、修订修复 |
| 上位机 | `sw-<主>.<次>.<修订>` | `sw-2.1.0` | 语义化版本 |
| 硬件 | `hw-<主>.<次>` | `hw-1.2` | 主版本改板、次版本改 BOM |
| 发布包 | `rel-<日期>-<硬件>-<固件>` | `rel-20261121-hw1.2-fw1.4.2` | 软硬件组合基线 |

**硬件版本与固件版本的对应关系必须记录在 `hardware/_released/compatibility.yml`**：

```yaml
compatibility:
  - hardware: hw-1.2
    firmware: [fw-1.3.0, fw-1.4.0, fw-1.4.2]
    released: 2026-11-21
```

## 5. 硬件资源分类

### 5.1 类别定义

| 类别 | 目录 | 内容 | 格式 | 版本策略 |
| --- | --- | --- | --- | --- |
| BOM | `hardware/bom/` | 物料清单 | CSV + XLSX | 跟硬件版本 |
| 原理图 | `hardware/schematic/` | 原理图源文件与 PDF | Altium/KiCad + PDF | 跟硬件版本 |
| PCB | `hardware/pcb/` | 布局源文件、Gerber、钢网 | 源文件 + Gerber ZIP | 跟硬件版本 |
| 结构 | `hardware/mechanical/` | 3D 模型、2D 图纸 | STEP + PDF | 跟结构版本 |
| 工装 | `hardware/fixture/` | 测试夹具、烧录工装 | STEP + 图纸 | 跟工装版本 |
| 元器件资料 | `hardware/datasheet/` | 规格书、认证报告 | PDF | 跟料号 |
| 已发布 | `hardware/_released/` | 冻结的发布包 | 归档 | 只读 |

### 5.2 BOM 规范

BOM 是硬件资源的核心，必须结构化且可校验。

**必填列**：

| 列 | 说明 | 校验 |
| --- | --- | --- |
| 序号 | 行号 | 唯一、连续 |
| 位号 | R1,R2,C3 | 与原理图一致 |
| 物料编码 | 内部料号 | 存在于物料主数据 |
| 描述 | 规格描述 | 非空 |
| 封装 | 0402/QFN-32 | 与 PCB 一致 |
| 数量 | 单板用量 | > 0 |
| 制造商 | 品牌 | 非空 |
| 制造商料号 | MPN | 非空 |
| 车规等级 | AEC-Q100/Q101/Q200/NA | 汽车电子必填 |
| 替代料 | 允许的替代 MPN | 可选 |
| 关键件 | 是/否 | 关键件需双源 |

**BOM 版本**：`BOM-<硬件版本>-<修订>`，如 `BOM-hw1.2-A`。

**变更规则**：任何 BOM 变更必须关联 ECN；变更后硬件次版本号 +1。

### 5.3 硬件资料元数据

二进制文件无法写 front-matter，因此在同目录维护 `manifest.yml`：

```yaml
version: hw-1.2
released: 2026-11-21
items:
  - path: schematic/PCU24-MainBoard-v1.2.SchDoc
    type: schematic
    revision: C
    owner: 李工
    sha256: 9f2c...
  - path: pcb/PCU24-MainBoard-v1.2.GBR.zip
    type: gerber
    revision: B
    owner: 李工
    sha256: 3a71...
  - path: bom/BOM-hw1.2-A.csv
    type: bom
    revision: A
    owner: 王工
    sha256: c81d...
```

**校验**：每次提交硬件资料，系统重算 `sha256` 并与 manifest 比对；不一致则拒绝提交并要求更新 manifest。

## 6. 分类路由算法

执行器产出文件后，按以下顺序判定归属：

```
1. 读取产物元数据（front-matter / manifest / 文件名）
2. 若含 type 且 type ∈ 文档类型表 → 文档资产
3. 若扩展名为 .c/.h/.cpp/.py/.ts 等且位于代码目录 → 代码资产
4. 若扩展名为 .SchDoc/.GBR/.step/.csv(BOM) → 硬件资产
5. 若无法判定 → 拒绝落盘，抛出结构化问题
6. 校验：路径、命名、元数据、模板必填字段
7. 落盘并按规则更新索引与追溯矩阵
8. 生成提交信息与 PR 描述
```

**拒绝落盘的情况**：

- 文件名不符合命名规范；
- 文档缺少必填 front-matter；
- 文档类型不在注册表中；
- 硬件文件缺少 manifest 条目；
- 目标路径与分类编码不一致。

## 7. 索引与追溯

### 7.1 文档索引

`docs/_index/documents.csv`：

```csv
id,title,stage,type,revision,status,owner,updated,path
DOC-S1-SRS-002,整机需求规格书,S1,SRS,v2.0,released,赵工,2026-11-10,docs/S1-策划/SRS/SRS-PCU24-002-整机需求.md
```

### 7.2 追溯矩阵

`docs/_index/traceability.csv`：

```csv
requirement,designDoc,dfmeaItem,specialCharacteristic,processStep,pfmeaItem,controlPlan,testCase,commit,hardware
REQ-001,DOC-S2-DFMEA-012,DFMEA-012,CC-03,OP-20,PFMEA-020,CP-020,TC-045,a1b2c3d,hw-1.2
```

系统在每次工单完成时自动追加行，并校验：

- 每个需求至少有一条设计文档；
- 每个特殊特性至少有一条控制计划；
- 每个控制计划至少有一条测试用例。

缺失即在面板标红。

## 8. 归档与作废

| 动作 | 规则 |
| --- | --- |
| 修订 | 原文件保留，`revision` +1，旧版本移入 `_archive/<原路径>/` |
| 作废 | `status: obsolete`，移入 `_archive/`，追溯矩阵保留引用 |
| 删除 | 禁止直接删除已发布文档；只能作废 |
| 恢复 | 从 `_archive/` 恢复需新工单与授权 |

## 9. 自动分类的边界

系统能自动做：

- 按模板生成文档骨架；
- 按规则判定类型与路径；
- 校验字段与一致性；
- 更新索引与追溯矩阵；
- 生成提交与 PR。

系统不能自动做：

- 判断技术内容的正确性；
- 决定特殊特性的等级；
- 批准文档发布；
- 替代设计评审。

## 10. 快速检查清单

执行器在提交前自检：

- [ ] 文件路径符合 `docs/<阶段>/<类型>/` 或对应资产目录
- [ ] 文件名符合 `<类型>-<项目>-<流水>-<简述>`
- [ ] front-matter 必填字段齐全
- [ ] `id` 与路径一致
- [ ] 模板必填章节无空缺
- [ ] 上下游追溯链接有效
- [ ] 硬件文件已在 manifest 登记且哈希匹配
- [ ] 提交信息含工单号
- [ ] 未触碰禁止分支
