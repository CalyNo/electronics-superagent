# 10 存量项目迁移

> 本文回答一个问题：**已经在跑的项目（本地目录、共享盘、老 Git 仓库），怎么接进这套系统。**
> 新项目从零建仓见 [09-新项目接入](09-新项目接入.md)；目录与命名规则见 [03-资产分类规范](03-资产分类规范.md)。

## 1. 先纠正一个默认假设：迁移不是搬家

绝大多数人第一次做这件事，动作都是"把文件整理进 `docs/S2-产品设计/DFMEA/` 这样的目录"。这是错的，而且是最容易造成不可逆损失的做法。

因为系统真正需要的东西，按重要性排序是这样的：

| 优先级 | 系统需要什么 | 没有它的后果 | 有它但目录乱 |
| --- | --- | --- | --- |
| 1 | **可解析的元数据**：每份文件的资产 ID、阶段、类型、状态、版本 | 系统读不懂存量，只能当普通文件 | 完全可用 |
| 2 | **可反查的追溯关系**：需求→DFMEA→特殊特性→控制计划 | 审核问询无法自证，PPAP 齐套全靠人肉 | 完全可用 |
| 3 | **可审计的历史**：Git 基线、谁在什么时候改了什么 | 无法界定责任，变更不可回溯 | 完全可用 |
| 4 | **物理位置整齐**：文件躺在分类目录里 | 人找文件慢一点 | 无影响 |

**物理位置排在第四位，而它恰恰是唯一不可逆的一项。** 改名会让客户提交件、体系文件、历史评审记录里的引用全部断裂；移动会让"这份文件到底是不是当初交付的那一版"无法自证。前三个都能事后补，第四个做错了补不回来。

所以本文的核心策略是：**先建逻辑索引（1、2），再冻历史（3），物理整理放到最后，能不动就不动。**

## 2. 四种接入形态

判定标准不是"文件多不多"，而是**这批文件有没有对外交付过**。

| 形态 | 适用条件 | 是否移动文件 | Git 历史 | 默认 |
| --- | --- | --- | --- | --- |
| **M1 原地加装** | 已有 Git 仓库；文件已发布/已交付/被体系文件引用 | ❌ 不移 | 保留原仓库与全部历史 | ✅ 默认 |
| **M2 快照重建** | 本地目录无 Git；或历史里混入密钥、大二进制、必须清洗 | ✅ 复制进新仓 | 新仓，首个提交是 as-is 快照 | 无 Git 时 |
| **M3 分区纳管** | 大量未发布草稿；项目刚开始不久，包袱轻 | ✅ 仅未发布件移入分类目录 | 同 M2 | 仅轻包袱 |
| **M4 平台合并** | 与既有平台同源，需共享 BSP/主板，且已决定走 09 的形态 B | ❌ 加 `projects/<CODE>/` | 保留（subtree 或 filter-repo） | 满足条件时 |

**为什么默认 M1**：迁移的风险与"被移动的文件数"成正比，而与"文件总数"无关。不动路径，追溯链、客户引用、工程师肌肉记忆全部保持不变，这是唯一能在不惊动质量体系和客户的前提下接入的方式。

**M2 的触发条件要说清**：不是"没有 Git 就要重建"，而是"没有 Git，或者历史本身就是负担"。历史里如果有明文密钥、有 2GB 的 PCB 备份、有买了三年又删掉的中间件，那这份历史不是资产而是负债——重开一个干净的仓库、把当前状态做成第一个提交，比清洗历史便宜得多。

### 2.1 判定流程

```
这批文件有 Git 仓库吗？
├─ 有 ──> 历史里有明文密钥 / >50MB 二进制 / 大量已删除的大目录吗？
│         ├─ 有 ──> 能接受"全员重新 clone + 所有 commit hash 变化"吗？
│         │         ├─ 能 ──> git lfs migrate / filter-repo 清洗，仍走 M1
│         │         └─ 不能 ─> M1 + 新开一个仓给系统用，老仓只读归档（见 §7.2）
│         └─ 没有 ─> M1
└─ 没有 ─> 文件已交付给客户 / 已被体系文件引用吗？
           ├─ 是 ──> M2（快照重建，原名原结构进 Git，映射表兜底）
           └─ 否 ──> 文件量 < 500 且都是草稿？ ── 是 ─> M3
                                                 └─ 否 ─> M2
```

## 3. 迁移前必须回答的五个问题

这五个问题的答案决定后面所有动作，必须由项目负责人书面确认（写进 `.migration/decision.md`），不能由平台方代答。

| 问题 | 为什么必须先答 | 答错的代价 |
| --- | --- | --- |
| **冻结窗口从哪天到哪天？** | 迁移期间源目录不能有人改，否则盘点结果立刻失效 | 校验和不一致，映射表指向错误版本 |
| **哪些文件已对外交付？** | 这批绝对不能改名/移动 | 客户提交件与实物对不上，审核开不符合项 |
| **历史要不要保留？** | 决定 M1/M2，以及是否要重写 commit | 事后想保留已经来不及 |
| **谁负责逐份确认分类？** | 分类规则只能到"建议"，最终判定必须是人 | 错误分类进入索引，追溯链全歪 |
| **首批开放哪些能力？** | 决定 `stages.enabled` 与 Policy 白名单 | 一上来就全开，第一次出错就失去信任 |

## 4. 七步流程

配套脚本 `scripts/import-project.sh` 有四个模式，前两个只读、第三个只增、第四个只校验：

| 模式 | 作用 | 是否写源目录 | 产出 |
| --- | --- | --- | --- |
| `--scan`（默认） | 盘点：文件量、体积、Git 状态、大文件、疑似凭据、重名 | ❌ 只读 | 终端报告 |
| `--plan` | 生成分类建议、sidecar 草案、债务台账 | ❌ 只读 | `.migration/` 三份文件 |
| `--apply` | 加装骨架、建阶段目录、落位 sidecar、可选 Git 快照 | ✅ 只新增 | `.migration/manifest.txt`（回滚依据） |
| `--verify` | 校验骨架完整性、映射路径存在性、assetId 唯一、LFS | ❌ 只读 | 逐项 OK/FAIL |

`.migration/` 会被自动写进 `.git/info/exclude`，迁移产物不进基线、也不污染项目自己的 `.gitignore`。

| 步 | 动作 | 谁做 | 产出 | 验收 |
| --- | --- | --- | --- | --- |
| P0 | 冻结与盘点 | 平台 | 冻结通告、`sha256` 清单、盘点报告 | 源目录只读，清单可复算 |
| P1 | 敏感信息与大文件治理 | 安全 + 平台 | 清洗记录、LFS 迁移结果 | 密钥扫描零命中 |
| P2 | 骨架加装 | 平台 | 缺失文件补齐、`.superagent/` 三件套 | 未覆盖、未删除任何原文件 |
| P3 | 分类与映射 | 项目 + 平台 | `import-map.csv`、sidecar | 抽样 20 份可反查 |
| P4 | 索引与追溯重建 | 项目 | `documents.csv`、主干追溯边 | 三条主干边闭合 |
| P5 | 门禁接入 | 平台 | validators 的 `legacy` 模式、债务台账 | 空跑通过且不误报 |
| P6 | 注册与灰度 | 平台 | profile/stateDir/policy 条目 | `observe` 两周期决策正常 |

### P0 冻结与盘点

冻结不是"通知一下"，要有可执行的边界：

1. 对源目录做**全量校验和清单**（`find -type f -exec sha256sum`），这是后续一切比对的基准，也是"迁移没弄丢东西"的唯一证据；
2. 把源目录设为只读（Windows 去掉写权限 / Linux `chmod -R a-w`），或至少加一个 `README-MIGRATING.md` 说明"本目录 X 月 X 日前禁止修改，改动请提工单"；
3. 盘点四项数据：文件数与体积分布、Git 状态（分支/提交数/是否脏）、已交付件清单、敏感信息候选。

盘点用脚本做，不要人肉数：

```sh
scripts/import-project.sh /path/to/legacy --scan
```

输出示例（一个 1200 文件、3.2 GB 的老项目）：

```
源目录：/data/legacy/电机控制器_V2
文件数：1247   总体积：3.2 GB   Git：是（分支 3，提交 842，工作区有改动）
最大文件：Hardware/backup/PCB_full_2023.zip  412 MB  ⚠ 超阈值
疑似密钥：Config/secrets.h:12  API_KEY = "..."    ⚠ 阻断
重复文件名：DFMEA_电机控制器.xlsx ×3（不同目录）
文档候选：318 份（高置信 186 / 中置信 97 / 无法判定 35）
```

### P1 敏感信息与大文件治理

**这一步必须在基线冻结之前做完**，因为它是唯一需要重写历史的环节，而重写历史的成本随"已有多少人 clone 过"指数上升。基线一旦冻结、执行器开始接单，再动历史就等于让所有在跑的工单基线失效。

四类东西要处理：

| 类型 | 判定 | 处理 |
| --- | --- | --- |
| **凭据** | `*.env`、`*.key`、`secrets.*`，或代码里 `(api_key\|token\|password)\s*[:=]\s*"..."` | 换密钥（不是删文件），删除文件，加 `.gitignore`；历史里有的必须清洗 |
| **个人信息** | 8D 里的客户联系人手机号、员工身份证、客诉人姓名 | 脱敏后进库，原件移入受控目录（不进 Git） |
| **大二进制** | 单件 > 50 MB，或已被 Git 跟踪的 PCB/STEP/备份包 | `git lfs migrate import --include='*.PcbDoc,*.zip,*.step'` 后全员重新 clone |
| **多版本共存** | `v2.3 最终版.xlsx`、`v2.3 最终版(1).xlsx`、`v2.3 最终版_张工改.xlsx` | 不删除。选一份为权威，其余标 `status: obsolete` 并指向权威版本 |

关于 LFS 迁移的时机，规则很硬：**要么在 P1 做，要么永远不做。** 中途做等于让所有分支的基线漂移，执行器的 `Mandate` 记录的 tag 会指向不存在的对象。

### P2 骨架加装（只增不改）

这一步的原则可以压成三个"不"：**不覆盖、不删除、不移动**。

```sh
scripts/import-project.sh /path/to/legacy --apply --code PCU24 --stages S1,S2,S3
```

脚本只做四件事：

1. 把 `scaffold/` 里源目录缺失的文件复制进去（`.gitattributes`、`.github/`、`.superagent/`、`docs/_index/`、`tools/validators/`）；
2. 已存在的同名文件**一律不覆盖**，新版本写成 `<原名>.platform-new` 留给人工比对——因为源目录里那份 `.gitignore` 很可能有团队多年积累的例外规则，直接覆盖会立刻炸掉构建；
3. 按 `--stages` 创建阶段目录，未启用的阶段完全不建（与 09 §2.2 一致）；
4. 生成 `.migration/` 记录本次加装的文件清单与时间戳，作为回滚依据。

**关键的加装顺序**：先 `.gitattributes` 再 `git add`。反过来做，第一批提交的 PDF 就以普通对象进了历史，后面再转 LFS 要重写历史——同一个坑踩两次的团队不少。

### P3 分类与映射（核心工序）

这一步的产出是 `docs/_index/import-map.csv`，格式与 [09 §7.1](09-新项目接入.md) 一致：

```csv
oldPath,assetId,type,stage,status,note
03_设计输出/DFMEA_电机控制器_v2.3.xlsx,DOC-S2-DFMEA-001,DFMEA,S2,released,客户已批准，保持原名
02_需求/客户SOR_2024.pdf,DOC-S1-SRS-001,SRS,S1,released,sidecar 元数据
硬件/原理图/主板.SchDoc,HW-schematic-001,schematic,,released,权威标识见 hardware/manifest.yml
固件/src/main.c,,,,,代码不分配资产 ID，用路径 + commit 定位
```

三条分配规则：

- **文档**用 `DOC-<阶段>-<类型>-<三位流水>`，流水在项目内按类型全局递增，**作废不复用号码**（复用会让历史引用指向另一份文件）；
- **硬件**件在迁移期发 `HW-<type>-NNN` 便于引用，但**权威标识始终是 `hardware/manifest.yml` 里的 `path + sha256`**——因为硬件是二进制，同一路径不同版本必须靠哈希区分；
- **代码**不分配资产 ID。代码的身份是 `路径 + commit`，给它编资产号只会制造一个永远对不上的第二身份。

分类给三档置信度，不同档走不同流程：

| 置信度 | 判定依据 | 处理 |
| --- | --- | --- |
| **高** | 文件名含明确关键词（`DFMEA`、`控制计划`、`8D`）；或扩展名+所在目录都指向同一类 | 脚本自动采纳，人工抽查 10% |
| **中** | 仅路径语义（`03_设计输出/` 下）或仅扩展名（`.xlsx`） | 必须在映射表里逐条确认后才能进 `documents.csv` |
| **低 / 无法判定** | 文件名是 `新建文件夹/1.xlsx`、`最终版.docx` | 进 `_unclassified/` 列出清单，**不猜**，由项目负责人指派 |

宁可不分类，也不要猜错。一份被错误标成 `S2/DFMEA` 的会议纪要会污染特殊特性清单的推导，而一份留在 `_unclassified/` 的文件只是没被索引，随时可以补。

判定规则表（脚本内置，可通过 `taxonomy.yml` 扩展）：

| 关键词 / 模式 | 判定 | 置信度 |
| --- | --- | --- |
| SOR、RFQ、技术要求、客户规范 | S1 / SRS | 高 |
| 章程、charter、立项 | S1 / CHTR | 高 |
| APQP、项目计划、timing plan | S1 / APQP | 高 |
| 可行性、feasibility、成本分析 | S1 / FEAS | 中 |
| DFMEA、设计 FMEA | S2 / DFMEA | 高 |
| DVP、DVP&R、验证计划 | S2 / DVP | 高 |
| 特殊特性、CC/SC、关键特性 | S2 / SC | 中 |
| 流程图、PFC、过程流程 | S3 / PFC | 高 |
| PFMEA | S3 / PFMEA | 高 |
| 控制计划、control plan、CP | S3 / CP | 高 |
| MSA、GRR、Gage R&R | S4 / MSA | 高 |
| SPC、CPK、PPK、过程能力 | S4 / SPC | 高 |
| 试产、试作、pilot、run@rate | S4 / TR | 中 |
| PPAP、PSW、提交清单 | S4 / PPAP | 高 |
| 8D、纠正措施、CAR | S5 / 8D | 高 |
| ECN、ECO、PCN、变更通知 | S5 / ECN | 高 |
| BOM | `hardware/bom` | 高 |
| 原理图、SCH、schematic | `hardware/schematic` | 高 |
| PCB、Gerber、布局 | `hardware/pcb` | 高 |
| 结构、3D、STEP、外壳 | `hardware/mechanical` | 中 |
| 工装、治具、fixture、测试架 | `hardware/fixture` | 中 |
| datasheet、器件手册、规格书 | `hardware/datasheet` | 中 |
| `.c/.h/.s/.ld` 且路径含 `src`、`firmware` | `firmware/` | 高 |
| `.py/.js/.cs` 且路径含 `tool`、`gui`、`test` | `software/` 或 `test/` | 中 |

生成映射建议（不改源文件）：

```sh
scripts/import-project.sh /path/to/legacy --plan --out .migration
```

产出 `.migration/import-map.proposed.csv`、`.migration/sidecars/`、`.migration/legacy-debt.csv` 三样东西，人工确认后再放进 `docs/_index/`。

**二进制件必须配 sidecar**：PDF、Word、xlsx、客户图纸改不了 front-matter，就在旁边放 `<原名>.meta.yml`，内容与 front-matter 同构。不去改原文件——改了会破坏哈希，而哈希是"这份文件就是当初交付的那一版"的唯一证据。

### P4 索引与追溯重建

`documents.csv` 从 `import-map.csv` 派生，不要手工维护两套：

```csv
id,title,stage,type,revision,status,owner,updated,path
DOC-S1-SRS-001,客户SOR 2024,S1,SRS,v1.0,released,赵工,2024-06-11,02_需求/客户SOR_2024.pdf
```

`revision` 从文件名里的版本号提取（`v2.3`、`RevC`、`A版`），提取不到就写 `v0.0` 并在债务台账里标记——**不要编一个看起来合理的版本号**，`v0.0` 的语义是"版本未知"，而编出来的 `v1.0` 会让评审以为那是受控版本。

追溯矩阵只重建**能确证的边**。冷启动别贪多，先把三条主干边连起来：

```
SRS（需求条目）→ DFMEA（失效模式）→ SC（特殊特性）→ CP（控制项）
```

这三条边覆盖了 80% 的审核问询（"这个特殊特性怎么来的""控制计划为什么检这一项"）。其余的边（DFMEA→DVP、PFMEA→CP、CP→MSA）按同样的方式逐阶段补。

关联靠"文件名相似度 + 文档内容里的编号引用"给候选，**由人确认后才写入**。追溯矩阵造假在审核时是致命问题——一条编造的 `upstream` 边，比缺一条边严重得多。

### P5 门禁接入

存量件不可能一上来就满足模板要求，所以校验器要有一个 `legacy` 模式：

| 模式 | 行为 | 何时用 |
| --- | --- | --- |
| `strict` | 任何缺 front-matter、缺追溯、命名不合规都失败 | 新建项目、全部新文档 |
| `legacy` | 只校验**已登记**在 `documents.csv` 里的件；未登记件仅告警；缺追溯仅告警 | 迁移期，默认 6 个月 |
| `report` | 全部只告警不失败 | 迁移首月，仅统计 |

同时建**存量债务台账** `docs/_index/legacy-debt.csv`，把每笔债落到人头上：

```csv
assetId,debtType,detail,owner,due,status
DOC-S2-DFMEA-001,missing-frontmatter,无 id/stage 字段,李工,2026-12-31,open
DOC-S1-SRS-003,missing-traceability,无 downstream 边,赵工,2026-12-15,open
FW-MAIN,noncompliant-path,固件在 固件/src 而非 firmware/app,王工,2027-03-31,open
```

规则：**每周告警数必须下降**，不设总量目标只设斜率目标。定"三个月清零"这种目标的结果一定是有人批量造 metadata 应付检查，而造出来的 metadata 比没有更糟。

### P6 注册与灰度

平台侧动作与 09 §7 的第 4、7 步相同，差别在灰度更保守：

1. **Source 只挂一个群**，先只监听 `mentions`，不开 `all`；
2. **Policy 的 accept 模式设 `observe`**，跑满两周，逐条看决策记录：它认为该接的单是不是真该接，它认为不该接的是否漏了；
3. **首张真实工单选只读任务**——例如"生成当前文档索引的一致性报告"或"检查控制计划是否覆盖全部特殊特性"。不要第一单就让它改代码。第一次就翻车，团队后面半年都不会再信这个东西；
4. 观察期内出现的每一次误判，都当成规则缺陷修 `policy.example.yml` 或 `rules.yml`，而不是靠提示词打补丁。

## 5. 迁移成熟度：不必一次迁完

这是最需要讲清楚的一点——**迁移是渐进的，每一级都有独立价值**。很多团队卡在"要么全做完要么不做"，实际上 L1 就已经能拿到大部分收益。

| 级别 | 判据 | 已解锁能力 | 典型工期（1200 文件） |
| --- | --- | --- | --- |
| **L0 未迁移** | 文件在共享盘/个人电脑，无索引 | 无 | — |
| **L1 已纳管** | 进 Git 有基线；`manifest.yml` 完整；`import-map.csv` 覆盖已交付件 | 文档检索、齐套率统计、8D 起草、变更影响初筛 | 2–3 人日 |
| **L2 索引完整** | front-matter/sidecar 覆盖 ≥ 80%；三条主干追溯边闭合；CI 校验接入 | 一致性自检（PFC↔PFMEA↔CP）、ECN 影响分析、PPAP 齐套自检 | +5–8 人日 |
| **L3 全托管** | 新文档全部按模板产出；执行器可写代码与硬件目录；阶段门自动预检 | 全流程自动编排、门禁证据包自动组装 | +10–15 人日，且需 2 个迭代磨合 |

**建议的推进节奏**：L1 一次做完（一周内），L2 按阶段推进（每完成一个阶段的索引就放开该阶段的自动化），L3 等前两级稳定运行一个季度后再谈。跳过 L1 直接追 L3 的项目，最后通常连 L1 都没做成。

## 6. 工期与人力估算

| 源目录规模 | 已交付件占比 | 工作量 | 建议方式 |
| --- | --- | --- | --- |
| < 500 文件 | < 20% | 2 人日 | 一次性完成 L1+L2 |
| 500–2000 | 20–50% | 5–8 人日 | L1 一周，L2 分两批 |
| 2000–5000 | > 50% | 10–15 人日 | 按 APQP 阶段分批，每批独立验收 |
| > 5000 | 任意 | 15 人日以上 | 只迁"当前在产 + 未来 12 个月要动"的部分，历史版本整包归档不索引 |

**最后一行是最重要的经验**：文件数超过 5000 的老项目，全量索引的边际收益极低——绝大部分是历史版本、废弃方案、别人的中间稿。正确做法是划一条时间线（例如"2024 年后的在产项目"），线内精细迁移，线外整包打 tag 归档，需要时再按需索引。

## 7. 回滚

迁移必须可回滚，这是能不能说服质量部门点头的前提。

### 7.1 M1 原地加装（天然可回滚）

源文件一个都没动，回滚就是删掉新增的东西。**优先用 Git 回滚**，比按清单删更可靠——加装发生在快照提交之后且未提交，所以工作区相对快照的全部差异就是"我们加的东西"：

```sh
cd /path/to/legacy
git status --short | head          # 先确认差异只有加装内容，没有别人的未提交改动
git reset --hard                   # 回到 as-is 快照提交
git clean -fd                      # 清掉未跟踪的新增文件与目录（含 .gitkeep、sidecar）
rm -rf .migration                  # 迁移产物被 git 忽略，clean 不会动它，需显式删
```

没有 Git（未加 `--git-init`）时，用加装清单删：

```sh
cd /path/to/legacy
while read -r f; do rm -f "$f"; done < .migration/manifest.txt
rm -rf .migration .superagent tools/validators docs/_templates
find docs -type d -empty -delete   # 清理加装时建的空阶段目录
```

因为加装是纯新增，删除不会伤到任何原有内容。**这也是 M1 值得作为默认的第二个理由。**

注意两种方式都**不影响源文件**：回滚前后对已交付件做 `sha256sum` 比对，结果应当完全一致——这是回滚成功的判据，而不是"看起来没多东西"。

两个已知的例外，都不是问题但要知道：

- `--git-init` 时 `.gitattributes` 会在快照提交**之前**落位（否则二进制以普通对象入库，之后再转 LFS 就得重写历史），所以它属于快照的一部分，回滚后会保留。这是刻意的取舍。
- `.migration/` 被写入 `.git/info/exclude`，`git clean -fd` 不会删它（忽略文件需 `-x`，而 `-x` 会连带删掉项目自己的构建产物）。所以回滚脚本里显式 `rm -rf .migration`。

### 7.2 M2 快照重建

原目录保持只读不动，回滚 = 继续用原目录。新仓留着不删（它至少是一份完整备份），只是不接单。

如果已经重写过历史（LFS 迁移）且需要回退：

```sh
git lfs migrate export --include='*.PcbDoc,*.zip,*.step' --everything
```

注意：重写过的仓库，回退后所有协作方必须重新 clone，`reset --hard` 是解决不了的。

### 7.3 回滚的判断点

| 现象 | 判断 | 动作 |
| --- | --- | --- |
| 分类错误率 > 20% | 规则不适配本项目的命名习惯 | 停，改 `taxonomy.yml` 的映射后重跑 P3 |
| 已交付件无法反查 | 映射表有漏 | 补 `import-map.csv`，不必回滚 |
| 迁移后构建/编译失败 | 加装覆盖了原有配置 | 用 `.platform-new` 逐个比对恢复 |
| 团队拒绝使用新路径 | 移动了不该移动的文件 | 回滚到 M1，只做映射不做移动 |

## 9. 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 先把文件整理进分类目录再建索引 | 引用断裂、哈希失效，且不可逆 | 先映射，物理整理放最后 |
| 覆盖原有的 `.gitignore` / `.gitattributes` | 构建立刻失败，或大批文件误入 LFS | 一律写 `.platform-new`，人工合并 |
| 先 `git add` 再配 LFS | PDF/PCB 以普通对象进历史，之后要重写 | 先 `.gitattributes` 再首次提交 |
| 给没法确认的文件编一个版本号 | 评审误以为是受控版本，追溯链失真 | 写 `v0.0`（版本未知）并进债务台账 |
| 凭文件名推测追溯关系 | 编造的 `upstream` 边在审核时是致命问题 | 只写能确证的边，其余留空 |
| 全量索引 5000+ 文件 | 大量历史垃圾稀释索引质量，工期失控 | 划时间线，线外整包归档 |
| 迁移期就开 `auto` | 首单出错，团队失去信任 | `observe` 两周，首单选只读任务 |
| 迁移和 LFS 清洗混着做 | 出问题分不清是分类错还是历史错 | P1 一次做完历史治理，P3 只做映射 |
| 校验器直接上 `strict` | 存量件全部报错，CI 永久红 | 先 `report` 一个月，再 `legacy` 半年 |
