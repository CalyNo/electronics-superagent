## 2. 通用填写规则

### 2.1 必须保留的结构

每个模板包含四段固定结构，**不得删除或重排**：

1. **front-matter**：YAML 元数据，供校验与索引。
2. **文档信息表**：人读的版本与责任人信息。
3. **正文**：按章节填写，标注"必填"的章节不得为空。
4. **审批栏**：签署人与日期。

### 2.2 填写约定

| 约定 | 说明 |
| --- | --- |
| `<>` | 占位符，必须替换 |
| `[ ]` | 复选，按需勾选 |
| `TBD` | 待定，必须在提交评审前消除 |
| `⚠ 待补充` | 模型不确定的内容，必须由人确认 |
| `—` | 不适用，需在备注说明理由 |

### 2.3 禁止行为

- 删除必填章节；
- 编造数据或引用不存在的文件；
- 修改模板的标题层级与固定表格列；
- 在正文中嵌入未脱敏的客户信息或密钥。

### 2.4 校验规则

执行器提交前自动检查：

| 检查 | 失败后果 |
| --- | --- |
| front-matter 必填字段 | 拒绝提交 |
| `id` 与路径一致 | 拒绝提交 |
| 必填章节非空 | 拒绝提交 |
| `TBD` 数量 > 0 | 允许草稿，禁止转 `review` |
| `⚠ 待补充` 数量 > 阈值 | 禁止转 `review` |
| 追溯链接有效 | 拒绝提交 |
| 审批栏完整（转 `released` 时） | 拒绝发布 |

## 3. 使用流程

```
1. 执行器根据任务类型选择模板
2. 复制模板到目标路径，替换 front-matter
3. 填充已知字段（项目、阶段、责任人、关联需求）
4. 生成正文草稿，不确定处标 ⚠ 待补充
5. 运行校验，修复问题
6. 提交 PR，通知责任人
7. 责任人补充、评审、签署
8. 状态流转：draft → review → released
```

## 4. 版本与归档

| 动作 | 规则 |
| --- | --- |
| 修订 | `revision` +1，旧版移入 `_archive/` |
| 作废 | `status: obsolete`，保留引用 |
| 恢复 | 需新工单与授权 |

## 4.1 测试报告（TEST）的交付格式

测试报告是唯一**以 Word 为交付件**的文档类型：

- 受控源用 `17-测试报告.md`（供生成与校验）；
- 最终交付必须导出为 `.docx`（首选）或 `.doc`，沿用企业《测试报告模板》的表格样式与页眉图文；
- Markdown 不得作为交付件；导出后放置 `<同名>.docx.meta.yml` sidecar 记录 id 与 sha256；
- 详细要求见技能 `skills/iatf-test-report/SKILL.md`。

## 5. 与体系文件的关系

本模板集是**执行层模板**，需与企业 IATF 16949 体系文件对齐：

- 若企业已有 APQP 程序文件，以其为准，本模板做适配；
- 若客户有特殊要求（CSR），在模板中增加"客户特殊要求"章节；
- 模板变更需质量代表确认后发布新版本。

## 6. 快速开始

```bash
# 复制模板到项目仓库
cp -r templates/ <repo>/docs/_templates/

# 新建一份 DFMEA
cp <repo>/docs/_templates/05-DFMEA.md \
   <repo>/docs/S2-产品设计/DFMEA/DFMEA-PCU24-012-功率级.md

# 替换 front-matter 后填写
```
